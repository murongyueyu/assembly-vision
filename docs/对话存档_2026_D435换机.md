## 2. ★★ 三个独立根因（逐个排除才通）

> ★ 教训写在最前面：**三个问题叠在一起**，任何一个单独看都像"相机坏了"。
> 排查时**先把每个现象单独证伪**，不要一上来就动手刷固件。

### 根因 1：`cv2.VideoCapture` 在这台相机上**永远打不开**

| 检查 | 结果 |
|---|---|
| OpenCV 5.0 扫 MSMF / DSHOW / 默认后端 × 索引 0~5 | **全部 `isOpened()=False`** |
| 工程自带 `tools/probe_camera.py`（8 种分辨率） | 全部打不开 |
| 注册表 | D435 的 RGB / Depth 接口**历史上装过**，挂的是 Windows 通用 UVC 驱动 `usbvideo`；**从没装过 RealSense 驱动** |
| OpenCV 的 obsensor 后端 | `Camera index out of range` |

**根因**：D435 **不是普通 UVC 摄像头**，不被 OpenCV 按「相机索引」枚举。

**修法**：改用 Intel 的 SDK。装了 `pyrealsense2` 2.59.1（与 `D:\03_Apps\RealSense SDK 2.0` 同版本）。

★★ **关键认知（用户专门问过）**：
> `cv2.VideoCapture` 只管「图从哪来」，`cv2.imshow` 只管「图怎么显示」——
> **两者毫无关系**。`pyrealsense2` 给的就是标准 numpy BGR 数组，
> 和 `cap.read()` 给的完全一样。所以**分割、ROI 叠加、调试窗口一行都不用改**，
> 只有取图那 3 行要换。

**附带发现**：用户原脚本写的 `1280x480` **不是 D435 的任何原生模式**
（彩色只有 1920x1080 / 1280x720 / 640x480 / 424x240），SDK 只会报
`Couldn't resolve requests`。

### 根因 2：USB 口插在 2.0 上，链路只有 USB 2.1

**判据**：

```python
d.get_info(rs.camera_info.usb_type_descriptor)     # '2.1' 还是 '3.2'
```

实测（同一台相机、同一份代码，只换 USB 口）：

| 链路 | 640x480@30 | 424x240@6 | 结论 |
|---|---|---|---|
| **USB 3.2** | **30.0 fps**（60fps 也能开） | 立刻正常 |
| **USB 3.2** | 26.4 fps | — | 立刻正常 |

★ **关键推理**：`424x240@6` 只要约 2 MB/s，远低于 USB 2.0 的 ~40 MB/s。
所以「0 帧」**不是带宽不够，而是这条链路根本不工作** ——
**别浪费时间去调分辨率、降帧率、关自动曝光**。

**修法**：换到 USB 3 口。本机是 `MECHREVO KuangshiG16 PRO`，
注册表里 `PCI\CC_0C0330`（xHCI 控制器）+ `USB\ROOT_HUB30`（SuperSpeed 根集线器）
可以用来判断机器有没有 USB 3。

### 根因 3：RealSense Viewer 开着会**独占**设备

**症状**：SDK 能枚举到设备、能读能写传感器选项，但 `pipe.start()` 抛
`Device or resource busy`。

**修法**（按顺序）：关掉 Viewer → 仍不行则硬件复位：

```python
dev.hardware_reset()      # 之后等 6 秒让它重新枚举
```

★ 实测：USB 2.1 那会儿复位后从「busy」变成「能开流但 0 帧」——
**复位能解决"占用"，解决不了"链路速率"，两件事别混。**

### ★ 中途的一次误判（记录以免重犯）

`rs-enumerate-devices` 打印 `Camera Locked : YES`，一度被当成
「固件更新没跑完导致设备锁死」。**错。**

Intel 官方原话：

> The camera being locked is not a problem. The cameras of all RealSense users
> have the locked status. An 'unlocked' camera is a special one used by
> RealSense engineers to perform debugging of the camera.

（出处：<https://support.realsenseai.com/hc/en-us/community/posts/42608453911059-L515-Camera-locked?sort_by=votes>）

→ **未锁定**的才是工程调试机，这个字段对普通用户**没有诊断价值**。
★ 教训：一个看起来很像病因的字段，**先去查它到底什么意思**，别直接据此动手
（RealSense 固件**最多只能降级 20 次**，刷错了更麻烦）。

## 4.1 ★★ 一次自己的测量纠错：帧率「26.4fps 上限」是假的

> 这一段保留下来，因为**教训比结论更重要**。

**现象**：早先 `d435_fps_bench.py` 报「640x480@30 / 848x480@30 / 1280x720@30 /
1920x1080@30 **全部 26.4fps**」，我据此写下「26.4 是读帧循环的固定上限」。

★ **这个形态本身就是判据**：三种带宽相差 4 倍的流给出**完全相同**的数 ——
不可能是相机限制，只可能是**测量方法**卡住了。

**根因**：那一版脚本在测量循环里**每帧都做 `np` 统计 + 存图**，
Python 侧开销成了瓶颈，把相机真实帧率盖住了。

**修法**：纯读帧、不写盘、不做统计，并用**回调模式**（让 SDK 采集线程自己计数）
对照验证 —— 两个测法给出同一个数才算数。重测结果为 **30.0fps**。

★★ **顺带发现 60fps**：`rs-enumerate-devices` 打印的 profile 列表只列了
`640x480 → 30/15/6`，但**实际能开 60fps**（彩色、深度、红外都可以）。
→ 教训：**「工具说支持哪些模式」不等于「实际能开哪些模式」** ——
想要某个模式就直接 `cfg.enable_stream(..., 60)` 试一次。

★ **通用教训**：**看到「多个差异很大的输入给出同一个数」，先怀疑测量，别先下结论。**
这次差点把「D435 只能 26.4fps」当成硬约束写进 `AGENTS.md`。
## 4. 换机暴露的问题：木桌被当黄铜（§2.12 原话复现）

工位对准之前，先对着**笔记本 + 木桌**实测了一轮：

```
黄铜 86048 px = 全屏 28.0%，最大块 Ø328px（金属掩膜同量级）
过曝 0.00~0.10%    V 均值 112.7      → 曝光本身可用，不用先调
绿幕色相 H≈87~88（HBV 实测 83）       → 偏 4~5°，未进危险区
高饱和像素色相众数 H=88/87/89/86      → 没有 45~75 的危险峰
```

叠加图证实：**木桌整块被切进黄铜与金属掩膜**，连笔记本上的绿色贴纸也被判进去；
键盘（黑）、屏框、粉色鼠标判定正确。

→ **与 §2.12 的结论完全一致**：木桌的 H/S 与黄铜本就重叠，
**靠调阈值挡不住**（收紧会削掉零件自己的高光），
必须靠 **work_roi「位置即身份」+ 尺寸闸门（`max_diam_mm`）**。

★★ **换相机不会自动解决这一类假阳性** —— 它是「颜色空间本身不可分」，
与用哪台相机无关。**新相机 = 新光照 = 阈值必须重标**，但解法还是那两条。

## 5. ★★ D435 接入树莓派的可行性论证

> 结论先说：**可行，而且比 HBV 方案更有利** ——
> 因为它把 Pi 上**最重的那个负担（SGBM）整个消掉了**。
> 但**必须先实测 KCF 在 Pi 4B 上的成本**，那是新的瓶颈。

### 5.1 有利因素（逐条都有依据）

| # | 事实 | 为什么重要 |
|---|---|---|
| 1 | **`pyrealsense2` 有官方 aarch64 wheel** | PyPI 上 `pyrealsense2 2.59.1.11053` 提供 `manylinux2014_aarch64` 轮子（cp39 / cp310 / cp312）。**不需要从源码编译 librealsense** —— 那才是社区里最劝退的一步（要打内核补丁） |
| 2 | **Pi 4B 有 2 个 USB 3.0 口** | D435 **必须** USB 3（本项目已实测 USB 2.1 下 0 帧）。USB 3.0 的 5 Gbps 远超需求 |
| 3 | ★★ **深度由相机固件算，Pi 上不用跑 SGBM** | **这是换 D435 最大的收益**。工程文档 P0-5 写的「SGBM PC 15ms，按 6 倍估 Pi 上 ~90ms」**这条瓶颈直接消失** |
| 4 | 出厂标定齐全 | 内参、外参、深度标定都在相机里，**不用跑 c2**，也不用担心 Pi 上标定工具链不全 |
| 5 | 算法分层本来就干净 | `sources/` 是插拔式的，只吃 numpy；`core/` 不碰相机。换源不影响算法层 |

### 5.2 ★ 风险与需实测项（别只看好处）

| # | 风险 | 现状 / 判据 |
|---|---|---|
| 1 | ★★ **新瓶颈：KCF 的每目标成本** | PC 上 4 个目标 ≈ 32ms（KCF 约 8ms/目标）。**Pi 4B 单线程性能约为 PC 的 1/5~1/8**，粗估 4 目标会到 **150~250ms/帧 → 只有 4~7fps**。<br>**必须实测**：`tools/part_track_demo.py --bench` 在 Pi 上跑一次 |
| 2 | **供电** | Pi 4B 每个 USB 口额定 **900mA**，D435 额定约 5V/900mA（峰值更高）。加上板子自身 600~900mA，**很紧**。→ 用 5V/3A 以上电源；必要时上**带供电的 USB3 HUB** |
| 3 | **`pyrealsense2` 的 Python 版本匹配** | aarch64 轮子只有 **cp39 / cp310 / cp312**（**没有 cp311**）。<br>→ Pi 上要用 **64 位** Raspberry Pi OS，并把 Python 对上（Bookworm 默认 3.11 需注意；必要时用 3.10/3.12） |
| 4 | **udev 规则 / 权限** | pip 装的 `pyrealsense2` 自带 pyusb 后端，**需要 udev 规则**才能非 root 访问；否则要用 `sudo` 跑 |
| 5 | **与系统 OpenCV 共存** | pip 的 `pyrealsense2` wheel **不捆绑 OpenCV**（它自带的是导入示例里的可选依赖），Pi 上仍用系统的 `python3-opencv` 即可；★ 注意别让 pip 把 numpy 换成与系统 OpenCV ABI 不兼容的版本 |
| 6 | **CPU 之外的显存/带宽** | 深度流本身在 USB 3 上带宽充足；但 `rs.align`（深度对齐彩色）会额外吃 CPU —— 若只做「取件/装配」判断，**可以不对齐**，省一笔 |
| 7 | **固件未验证** | 本次把固件升到了 5.17.3.10。★ **5.15.1.55 是"能出图"的那个版本**（USB2.1 时都能跑到采样阶段）。若 Pi 上出现异常，**回退固件是可用的退路**（`rs-fw-update.exe -f <bin>`；注意固件最多降级 20 次） |

### 5.3 建议的验证顺序（上 Pi 之后按这个走）

1. `python3 -c "import pyrealsense2"` —— 确认轮子装上了、能 import
2. `rs-enumerate-devices`（或本项目的探针）—— 确认 **USB = 3.2**、SN 对得上
3. **`tools/part_track_demo.py --bench`** —— ★ **先测帧率，再谈别的**。
   这一步直接决定「Pi 4B 够不够用」；不够就得降分辨率/减目标数/换 Pi 5
4. 再跑离线回归 `python tests/run_all.py`（10/10）确认算法层没被环境搞坏
5. 最后才做真机全流程

### 5.4 一句话结论

> **D435 上树莓派在软件栈上没有拦路虎**（有官方 aarch64 轮子），
> 而且**消掉了 SGBM 这个原有瓶颈**；
> **真正的未知数是 Pi 4B 的 CPU 能不能扛住 KCF 的多目标成本** ——
> 这个**必须实机实测**，不能靠估算拍板。

## 8. 用户新增架构性需求：追踪算法对比选型（只记录，未实施）

> ★ **本节只记录需求与验收协议，不改代码。**
> 真正动手属 **A 模块**（`core/part_tracker.py`），按 `AGENTS.md` §0 铁律须**另开对话**。
> 完整版见 `AGENTS.md` **§6.5 P1-2**。

### 8.1 用户原话（要点）

> 「追踪算法可以用**抽帧**，而不是每帧运算。而且**识别只需要前面识别就好**，
> 不需要一直识别消耗算力。用**卡尔曼滤波追踪**，**KCF 感觉不太好用**。
> 但两个都可以试一试或者用其他的追踪算法。
> **最后选追踪算法的时候要对比，要有数据。**
> 不过比较追踪算法是后面的事情。」

### 8.2 先核实现状 —— 有一条已经做到了

| 用户的要求 | 现状 | 依据 |
|---|---|---|
| **抽帧** | ✅ **已实现** —— `detect_every_n: 5`，其余帧只跑追踪 + 绘制 | `part_tracker.py` docstring |
| 识别不必一直做 | 🔶 **部分** —— 检测帧才分割+识别，但检测帧本身仍做全图分割 + 分类 | 同上 |
| 用卡尔曼滤波 | ✅ **已有** `KalmanXY`（匀速，状态 `[x,y,vx,vy]`），轨迹误差 **2.312 → 1.286 px** | 实录 §2.20 |
| KCF 不好用 | 🔶 有实测支撑，但**文档自相矛盾** | 实录 §2.20/§2.21 |
| 要数据驱动对比 | ⬜ **尚未做** | — |

### 8.3 ★★ 一处必须一并修掉的文档矛盾

`part_tracker.py` 模块 docstring **第 29 行**仍写着：

> `backend` 可选 mosse/kcf/csrt：**Pi 上建议 `mosse`（2ms）**或 `kcf`（12ms）。

而 **§2.21 的实测结论是「后端只有 `kcf` 可靠」**：
**MOSSE 的 `update` 恒返回 False（实测 40/40 全丢）**。

→ 那句话是**过期的错误建议**。不修掉，接手的人会照它去选一个已知不能用的后端。

### 8.4 为什么「KCF 不好用」是真的 —— 三条实测证据

1. **每目标固定成本高**：实测 **5.5ms/目标**（另一处记 8ms），4 目标 ≈35ms/帧，
   且**与整帧尺寸无关** → 降分辨率省不下来。
2. **裁剪加速已试过并放弃**：**只快 14%，但静止漂移从 2.76px 崩到 131px**
   （裁剪窗滑动逼着反复 `init`，而 init 既不快又破坏追踪器状态）。
3. ★★ **返回值不可信**：**纯灰背景上（根本没有零件）`cv2.TrackerKCF.update()`
   依然返回 `True`** → **绝不能用它的返回值判断"零件还在不在"**
   （曾导致幻影轨迹判据失效，见实录 §2.27~2.29）。

★ 但它也有个优点要记着：**目前唯一在真机上稳定跑通的**（中位 28.9fps、相机上限 31）。
换掉它之前，必须证明替代品在**遮挡与身份冻结**上不退化。

### 8.5 ★ 「识别只做一次」的代价（不能只看省算力）

本项目被"检测不够频繁"咬过**两次**，都是**幽灵轨迹**类问题：

- §2.27 缺件不报 —— 当时判据用"轨迹在不在槽里"，而非**全图检测的权威结果**
  → 必须用 **`seen_ids`（来自全图检测）** 判。
- §2.28 / §2.29 料盘外幽灵轨迹 + 「全图搜 0 帧」
  → 新轨迹的块**必须先能被认成零件**（0.60）；`miss_streak`
  **不能在遮挡期间累计**。

→ 折中方案：**关键事件触发低频复检**（抽件 / 放装配位 / 遮挡解除 / 残差越限），
且 `detect_every_n` 应有上限、超过改为**按时间** ——
换 D435 后 60fps 与 30fps 下同样的 `every_n=5` 分别是 12 次/秒与 6 次/秒，
**语义完全不同**。这是换机后新出现的坑。

### 8.6 ★★ 对比协议（用户明确要求「要有数据」）

**先声明接口，再换实现** —— 否则分不清差异是算法还是调用方式造成的。

| 项 | 要求 |
|---|---|
| 统一接口 | `init(frame,bbox)` / `update(frame)->(ok,bbox)`；**5.x 与 4.x 两套 API 都兼容** |
| 候选 | ① **纯卡尔曼**（无外观模型）② `kcf`（基线）③ `csrt` ④ 其它（如 `vit`）⑤ 模板匹配 / 光流 |
| 素材 | ★ **固定同一段视频**（含遮挡/快速移动/静止/出画面）+ 合成序列 |
| 真值 | 合成序列用已知位置；真机用人工标注或"检测帧结果"（★ 后者有偏，须写明） |
| 指标 | 中心误差 px（均值/中位/p95）、跟随丢失率、**身份切换次数**、静止漂移 px、每目标耗时 ms、整机 fps |
| 分场景 | 静止 / 匀速 / 遮挡 0~85% / 遮挡解除后恢复 / 出画面再回来 |
| 反例判据 | ★ **纯灰背景必须返回"没在跟"**（KCF 正是栽在这条） |
| 门槛 | 真机 **≥28.9fps**、静止漂移不劣于 **2.76px**、遮挡行为不退化 |

**顺序**：PC 离线 → 真机 → Pi（别把"换算法"和"换算力平台"两个变量一起动）。

★★ **换 D435 之后必须重跑这套对比** —— 分辨率、GSD、帧率上限都变了
（640×480 可 30 或 60fps，GSD 0.795 或 0.397），相对优劣**可能跟着变**。
