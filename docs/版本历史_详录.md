### rev.3n 变更要点（本轮）— ★★ 尺寸闸门 + `work_roi_mode`（木桌假阳性）

> 模块：**A. 零件分割 / 识别 / 追踪**（单模块铁律）。对话存档：
> [对话存档_2026_木桌假阳性.md](https://github.com/murongyueyu/assembly-vision/blob/9a75fec00d105fd75043be023bce2793a8c4dc66/docs/%E5%AF%B9%E8%AF%9D%E5%AD%98%E6%A1%A3_2026_%E6%9C%A8%E6%A1%8C%E5%81%87%E9%98%B3%E6%80%A7.md)；坑：实录 **§2.42**。

**为什么做这个**：P0-0 的第 4 步（也是 P1-1「开放位置」的实现要点 1~3）。
在"曝光 → 色域 → 木桌假阳性"三步里，**只有它不依赖"相机架到工位"** ——
判据数字早已实测齐备，离线就能做完并写测试，所以本轮先做它。

**为什么只能靠几何**：木桌 H=19 / S=122 落在黄铜区间 `h∈[10,45] / s∈[50,180]` 内，
换 D435 后照样复现（实测黄铜 86048px = 全屏 28.0%）——
**换相机不解决"颜色不可分"**。而单独收紧 `h_max`/`s_max` 会削掉真零件自己的高光
（零件 S 上限 109、H 上限 45，与木桌区间本就重叠）。所以只能靠位置 + 尺寸。

**判据与阈值**（`segment.max_diam_mm: 120`）：

| 对象 | 面积 | 等效直径 `2·√(面积/π)` |
|---|---|---|
| 木桌（全图分割） | 31795mm² | **201mm** |
| 轮盘（真零件里最大） | 3300mm² | **64.5mm** |
| 底座 | 2258mm² | 54mm |

两者差 **2.7 倍**；取 120 则在两侧留 1.86 / 1.67 倍余量。
★ 用**等效直径**而不是外接框：真零件之间外接框很接近（槽 Ø75 / Ø65），
而等效直径直接对应"这块有多大"。

**两条顺序铁律**（原设计只写了第 2 条，第 1 条是踩了才知道）：

1. **闸门必须量「闭运算之前」的连通域**。`morph_close` 会把**相距 1~2px** 的块连成一块，
   而木桌就贴在零件旁边（真机上木桌下沿 y=204 比料盘上沿 y=187 还低）——
   拿闭运算后的掩膜量，得到的是「木桌 + 贴着它的零件」一整块，
   **整块超限 -> 连真零件一起剔掉**。实测（`test_size_gate` 场景 4）4 个零件只剩 2 个。
   修法：`_mask(..., morph=False)` 出一份"纯色域骨架"专门给闸门量尺寸，
   再拿 `keep_mask` 裁**闭运算后**的掩膜。
2. **闸门必须建在 `metal_mask` 之前**，并用已过滤的 brass 连通域**外扩 6mm**
   （`metal_keep_margin_mm`，球头 Ø5mm 会伸出零件轮廓）裁 metal 掩膜。
   否则木桌照样进 metal 掩膜 —— 实测木桌区 metal 占比曾达 **99.9%**，辐条扫优整个失效。

**两处偏离原设计**：

* `work_roi_mode` 做在 `Segmenter` 里，**没有**让 `work_roi_mask()` 返回全白 ——
  `part_track_demo.py` 拿同一张掩膜做「新轨迹只准建在工位内」的判断（实录 2.28/2.29
  的防幻影闸门），掩膜一变全白那道闸门会**静默失效**。
  ⇒ 掩膜照旧算（几何事实不变），"用不用它"由分割器决定。
* 闸门**不给 `mm_per_px` 时不生效**（静默关闭，完全退回旧行为）——
  老调用方（合成图工具、`calib/*`）与既有测试因此一行都不用改。

**真机对账**（`tools/verify_size_gate.py`，离线跑仓库里的实录帧，不需相机）：

| 帧 | 全图模式超大块 | 判定 | 该帧真零件最大 |
|---|---|---|---|
| `asm_raw.png` | **201.2mm** | 剔除 | 53.6mm |
| `assembly_choice.png` | **200.8mm** | 剔除 | 61.7mm |
| `tray_empty.png` | **204.6mm** | 剔除 | 35.5mm |

★★ 与上面表里记的「木桌 201mm」**逐位吻合**，而且这是**换 D435 之前**的 HBV 帧 ——
说明这条判据跨相机成立。附带确认 ROI 另把 4.6 万 px 压到 582~8054px，
**位置与尺寸两道闸门都在干活**。

**验收**：`tests/run_all.py` **13/13**（新增 `test_size_gate`）、
合成序列端到端 4 步全过、`tools/verify_size_gate.py` 退出码 0。

**没做**：`work_roi_mode` 保持 `work`，**没切 `full`** —— 代码就绪、离线已验证，
但要在工位实测木桌与零件的实际间隔、以及料盘外杂物（`tray_empty.png` 里那块
1246px 的偏绿黄块）的影响。★ 这一步**不阻塞**重跑 c3。

### rev.3k 变更要点 — 帧率结论纠错 + 追踪算法选型需求


> 与 `rev.3j` **同一天**、**同一个相机接入模块**，是它的两次追加：
> ① 纠正一条我自己写错的硬约束；② 记录用户新提的架构性需求。

#### ① ★★ 纠错：D435 能跑满 30fps，且 60fps 模式实际可开

**错在哪**：`rev.3j` 里写的「640x480@30 / 848x480@30 / 1280x720@30 / 1920x1080@30
**全部 26.4fps**，是读帧循环的固定上限」—— **这条结论已作废**。

**根因**：`d435_fps_bench.py` 在测量循环里**每帧都做 np 统计 + 存图**，
Python 侧开销成了瓶颈，把相机真实帧率盖住了。

★ **判据本来就在眼前**：三种带宽相差 4 倍的流给出**完全相同**的数 ——
不可能是相机限制，只能是**测量方法**卡住了。

**重测**（纯读帧 + **回调模式**双测法，两个测法同值才算数）：

| 模式 | 实测 |
|---|---|
| 彩色 640x480@30 / 848x480@30 / 1280x720@30 / 1920x1080@30 | **30.0 fps** |
| **彩色 640x480@60** | **59.9 fps** ← ★ 规格表里没有 |
| **深度 640x480@60 / 848x480@60** | **59.9 fps** ← ★ 规格表里没有 |
| **红外左目 640x480@60** | **59.9 fps** |
| **★ 彩色 + 深度 同时 640x480@60** | **64.5 / 64.5 fps** |

★★ **顺带发现**：`rs-enumerate-devices` 打印的 profile 列表**列不全** ——
它只列 `640x480 → 30/15/6`，但**实际能开 60fps**。
→ 教训：**「工具说支持哪些模式」不等于「实际能开哪些模式」**；想要就试一次。

★ **但要注意**：60fps 下每帧只给算法 16.7ms，而工程实测 **KCF 约 8ms/目标** ——
4 个目标就吃满 32ms。**提高相机帧率不会让算法变快**，反而更容易把算法逼到掉帧。
真正受益的是手工快速摆放/遮挡与多帧投票。

#### 修：手在画面里却显示「手: 无」（实录 §2.23）

用户截图里手套清楚地在压着料盘，面板却显示 `手: 无`；而同一次 `遮挡 100%` 是**对的**。

- **根因**：手指在 640x480 下**碎成 4~5 块**
  （`[(613,1.33),(502,2.04),(383,1.29),(278,1.27)]`），
  **没有一块超过 `min_area_px=3000`** -> 整只手被滤掉 -> `glove_bbox=None`。
  而 `glove_mask`（遮挡判定用）**没被清空**，所以**判定一直对、只有显示错**。
- **修法（两步）**：先闭运算把碎块连起来 `morph_close: 5 -> 21`
  （最大块 638 -> **3219**），再把闸门降到 `min_area_px: 2000`
  （有手 3219 = 1.6 倍余量；6 张无手帧未过滤最大蓝块**全部 = 0px**）。
- ★ `3000` **本身没错，是用法变了**：早期是"整只手 + 键盘背光"（真手套 83316px），
  现在是"几根手指搭在料盘上"（最大块 613px）。**一个阈值只在它被测出来的场景里有效。**
- ★ 我差点又犯错：量到"最大块 613"时想直接降阈值到 600 —— 但 **613 是"最大的一块"

#### 修：「完全被遮住」算遮挡，不算丢失（实录 §2.24）

用户指出：「被全部遮挡应该算遮挡还是丢失。但很显然我没有动底座应该算作遮挡。
只有当遮挡物全部移开之后…如果屏幕里面没有任何该零件的一小部分才应该算作丢失。」

- **原来错了**：`max_lost_frames = 12`（约 0.4 秒）就判 `lost`，
  而完全被手挡住时追踪器必然失败 -> **手搭上去半秒就报「丢失」，零件一动没动**；
  紧接着 `_prune()` 把轨迹删掉，"它应该在哪"这条信息也没了。
- **改成两个阈值 + 三个状态**：

  | 状态 | 含义 | 判据 |
  |---|---|---|
  | `occluded` | 还在原位，只是被挡（**含完全被挡**） | 失败时长 < `max_occluded_frames`(150≈5s) |
  | `lost` | 久到可疑，**但仍不删** | < `max_lost_frames`(300≈10s) |
  | `gone` | 已放弃，允许清掉 | >= `max_lost` |

- **`lost` 也不删**：删了就丢掉"它本来应该在哪"。手移开时 `_adopt` 会按 IoU/距离
  重新关联，**身份还在、位置也能恢复**。实测链路：`10 帧不可见 -> occluded`、
  `25 帧 -> lost`、**手移开 -> detected（恢复成功）**、`再遮 45 帧 -> 才清理`。
- ★ 教训：**状态机的"时长"参数，语义要先定清再选数字。**
  `12` 用在"快速剔除误检"上很合理，但用户要的是另一件事
  （「没动过的零件被挡住 ≠ 零件不在了」）—— **同一个计数器被两种语义抢用，
  所以怎么调都不对**。

#### 修：丢失判据按用户定义重写（实录 §2.25）+ 手套色域收紧 `h_min`（§2.26）

**① 丢失 = 「遮挡物移开后全图搜 2 秒无果」**（用户原话，我连错了两版）

| 版本 | 判据 | 错在哪 |
|---|---|---|
| 1 | 追踪失败 12 帧（0.4 秒）就 lost | 手搭上半秒就报丢失 |
| 2 | 追踪失败 150 帧（5 秒）才 lost | **计时起错了** —— 应从「遮挡物移开」起算 |
| **3（现行）** | 遮挡物移开后 `lost_grace_frames`(≈2s) 内**全图搜**不到 -> lost | —— |

- **盖着的时候永不判丢**（挡多久都不算，零件没动）；遮挡物一移开才启动计时。
- **「全图搜索」是硬要求**：`seen_ids` 必须来自覆盖全画面的检测，
  否则退化成范围搜索。demo 每 `--full-search-every`（默认 30 帧≈1s）
  跑一次不带 work_roi 的全图分割。
- ★ 两个「新建路径又漏了初始化」的坑（本模块第三次）：`ever_seen` 未置位 ->
  轨迹被当误检清掉；`judge_lost` 无条件覆盖状态 -> 刚检测到的也被标 occluded。

**② 手套色域 `h_min: 95` 是「刚好卡住」不是有余量**

用户提示「手套够蓝，框手其实也是色域分割」—— 对，`_mask(hsv, glove)` 本来就是色相带。

#### 修：幽灵轨迹 + 缺件不报（实录 §2.27）

用户两张真机截图：底座位置是空的却画着扭曲的橙色三角形（标「全图搜」），
且**底座没报缺件**；另一弧帧出现 **4 个幽灵**。

**幽灵轨迹（三个缺陷叠加）**
1. 匹配用的是**卡尔曼预测位置**（追踪失败后会漂移）+ 宽松的 `dist_match_px=40`
   -> 轨迹**抢到别处的块** -> 轨迹数虚增/错配。
   修：改用 `last_centroid` / `last_bbox`（**最后一次真正检测到**的位置）。
2. 匹配是「按列表顺序贪心」 -> 先遍历到的轨迹抢走后一条更该拿的块。
   修：**全局最优认领**（配对排序后从高到低，轨迹与块各用一次）。
3. `visible_ratio == 0` 时仍照画旧 `contour` -> 就是那些扭曲三角形。
   修：不可见时**不画轮廓**，改画空心圈+放射线。

**缺件不报**：`missing` 原来判「有没有轨迹落在这个槽里」，
而幽灵轨迹正好压在底座上 -> 被当成「有件」。
修：改用**全图检测的权威结果 `seen_ids`**。

> ★ 教训：**「某个东西在不在」要用检测结果判，不要用追踪状态推。**
> 追踪状态是「我记得它在那儿」，检测结果才是「我看见它了」。

**顺带修开销**：全图搜索改为**轻量识别**（只认面积像零件的块，
不跑 `check_slots`）：每帧均摊 39.8 -> **34.4ms**；
长时间看不见的轨迹跳过 KCF。真机中位 **27~28 fps**（相机上限 31）。

详见 `docs/踩坑实录.md` **§2.20 ~ §2.27**。
#### 修：面板缺件恢复 + 去掉「全图搜 0帧」标记 + 幻影轨迹短命（实录 §2.28 / §2.29）

**① 面板「缺: xxx」恢复**（我上一轮理解错了用户的意思）
用户原话：「不是去掉面板上的缺什么，而是不在画面显示某个物品缺失前的那个橙色标记」
顺带修了一个顺序 bug：`miss_txt` 在 `putText` 之后才赋值 -> `UnboundLocalError` 直接崩。

**② 画面上不再画「全图搜 0帧」**
「0 帧」= 轨迹刚诞生、一次都没跟住过（从噪声里生的）-> `draw()` 直接 `continue`。

**③ ★★ `miss_streak` 不能在遮挡期间累计**（第三次「一个计数器两种语义」）
实测：手盖 60 帧 -> `miss_streak=60`；手一移开再 30 帧就超过幻影阈值
-> **一个真实存在、一动没动的零件被删了**。
修：遮挡期间清零 —— **被遮挡不是不存在的证据**。
三次同类：`lost_frames`（§2.28）/ `clear_frames`（§2.25）/ `miss_streak`（§2.29）。

**④ 尝试过的两种错判据**
· `not adopted_once`（从未被检测匹配过）—— 轨迹**就是检测建的**，条件**永远不成立**，删除逻辑从来没跑到过
· `t.tracked_once`（KCF 报成功）—— 实测在**一帧纯灰背景**上
  `cv2.TrackerKCF.update()` **依然返回 True**（它自己找个东西盯上）-> **不能用追踪器返回值判幻影**

**⑤ 最终幻影判据**：`not covered and miss_streak > phantom_miss_frames`，
`phantom_miss_frames = max(90, lost_grace_frames * 3)`（从宽限期**推导**，不写死）。

**⑥ 防幻灵的两道闸**：位置（ROI **先内缩 6px**，因为 `work_roi` 是外扩 25mm 的）
+ 身份（新轨迹的块**必须能被认成某种零件**，得分 >= 0.60）。
实测 `now_raw.png` 里料盘外那块 600px 噪声**被认成 P2_column 0.89**，只有位置闸能挡。
新工具：`tools/verify_allow_new.py`。

验证：回归 10/10；真机中位 26.9 fps 退出码 0；
遮挡对照图分级正常（0%->detected 30%->tracked 50%+->occluded）。

详见 `docs/踩坑实录.md` **§2.20 ~ §2.29**。

### rev.3f 变更要点（本轮）


**★ 真机联调暴露的假 NG：轮盘明明装好，却报「缺失 辐条 5/8」。**

**根因**：`count_spokes` 把半径带切成 `n_radii_bands=3` 个子带各自数峰，
再「取众数、**并列时取较小值**」。真机实测（30~35mm 切 3 带，每带仅 1.67mm ≈ 1.9px）：

```
带(mm)        med    p95-med  阈值    峰数
30.0~31.7    0.000   1.000   0.600    8   <- 球头只落在最内侧这个带
31.7~33.3    0.000   1.000   0.600    6
33.3~35.0    0.000   1.000   0.600    5
```

`[8,6,5]` **三个全不同、没有众数** -> 并列取小 -> **5** -> `5 < required(8)` -> 假 NG。

而同一帧**整条 30~35mm 一次数**（c5 的做法）是 **8 峰、抖动 5.9°**。
**c5（标定）与 `check_assembly`（运行）在数同一批辐条却用了两套算法** —— 这才是真问题。

**修法**：按**角度均匀度**挑最好的带（真辐条是均布的，抖动最小远比票数最多可靠）：

```
select=vote(旧)     -> count=5  抖动=inf   峰=[98, 135, 177, 262, 309]
select=uniform(新)  -> count=8  抖动=6.2°  峰=[6.2, 57.2, 99, 135, 177, 218, 262, 309]
```

6.2° 与 c5 **独立**扫出的基线（5.9°）几乎逐度吻合 —— 互为独立验证。

- `polar.py`：新增 `spoke_jitter_deg()`；`count_spokes(select="uniform"|"vote")`
  ★ **这个判据不是新发明** —— c5 的 `sweep_band` 早就用它，这次是把同一条判据
    搬到 `check_assembly` 的路径上，让两处**用同一个标准**。
- `types.py`：`SpokeResult.jitter_deg`（新增字段）
- `workpiece.yaml`：`check.spokes.select: uniform` + `max_jitter_deg: 15.0`（含依据注释）
- `checks.py`：`check_assembly` 从配置读 `select` / `max_jitter_deg`
- `tests/test_polar.py`：新增「半径带选择策略」一节，钉住 uniform 行为

**★ 兜底**：所有候选带抖动都 > 15° 时**退回"峰最多"那个**，
让真缺陷被如实报出，而不是因为我们挑剔就报成 0（另一种假 NG）。

**验证**：

```
真机帧 asm_raw.png 上跑完整 check_assembly:
  修复前 verdict=NG  missing=[辐条 5/8]
  修复后 verdict=OK  spoke=8/8  抖动=6.2°  missing=[]
合成图 少画 0/1/2/4 根 -> 仍准确数出 8/7/6/4（真缺陷检出未变差）
回归 9/9 全绿；62 文件语法无误；端到端 OK
```

> ★ 一般教训：**同一个量在两个地方用了两套算法，迟早会打架。**
> **标定与运行必须共用同一条判据。**
