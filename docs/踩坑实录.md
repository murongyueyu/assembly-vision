### 2.5 相机的分辨率与拼接方式（实测，反直觉）

| 请求 | 实际 | 帧率 | 单眼 | 真双目? |
|---|---|---|---|---|
| 2560×960 | 2560×960 | **4.5 fps** | 1280×960 | ✅ |
| 2560×720 | 2560×720 | 4.5 fps | 1280×720 | ✅ |
| 1920×720 | →1280×720 | 48.7 fps | 640×720 | ✅ |
| 1280×960 | 1280×960 | 31.3 fps | 640×960 | ⚠️ 视场窄，左眼装不下料盘 |
| 960×960 | 960×960 | 32.0 fps | — | ❌ 单眼画面 |

**★★ 最终选用 `1280×480`（单眼 640×480）—— 与 `predict.py` 一致。**
判据是**左眼能不能看全料盘**（算法全程只用左眼）：

| 请求 | 单眼 | 左眼里的料盘 | 结论 |
|---|---|---|---|
| **1280×480** | 640×480 | 177×178 px（占宽28%） | ✅ **采用** |
| 1280×960 | 640×960 | 301×314 px（贴右边缘被切） | ❌ |
| 2560×960 | 1280×960 | — | ❌ **数字放大**，最糊 |

**三个反直觉点**：
1. **`2560×960` 不是真高分辨率，是数字放大**。判据：把高清缩回低清尺寸与原生低清比，
   差仅 **1.7**（几乎同一幅画）；而 `1280×960` 同法对比是 **26.6**（真不同）。
   再佐证：锐度 **1280×480=242 > 1280×960=125 > 2560×960=89**（越高越糊）。
   **分辨率高 ≠ 细节多**，判断真伪必须做"降采样回比对"。
2. **必须用左眼判断视场**，别用"完整拼接图看起来能放下" —— 算法只用 `f.left`。
3. **`scale.realtime` 会影响标定窗口里画面的大小**：取 0.5 时单眼 640×960 被缩成 320×480，
   标定窗口里料盘只有一半大，**看起来像"视野被裁了"，其实内容是全的**。标定取 **1.0**。

**帧率随 OpenCV 版本差异极大**：同一台相机，OpenCV **4.12** 下 2560×960 只有 **4.5 fps**，
OpenCV **5.0**（yolo 环境）能稳在 **31.9 fps**。**本项目统一用 yolo 环境的 OpenCV 5.0。**

### 2.8 料盘位姿自动补偿：不再依赖"料盘固定不动"

**为什么必须有**：整套判定原本建立在"料盘位置和朝向固定"上（c3 标一次单应，之后所有
槽位 ROI 都按那次算）。**实测踩过**：料盘在 c3 之后被挪了约 18mm ——
关键是**相机没动**：

```
绿幕质心   c3 (362.4,277.1) -> 现在 (366.2,272.8)   只差 3.8px   ✓ 相机没动
料盘暗区中心 c3 (417.5,258.5) -> 现在 (399.5,266.0)  差 18px      ★ 料盘动了
```

后果：四个槽的 ROI 全偏 18~20mm，覆盖率从 0.6 掉到 0.2，**明明有件全判"缺件"**。

**做法**（`assemvision/core/tray_pose.py`）：**零件本身就是最好的基准点**。

```
① 第一遍：不依赖槽位坐标，按形状/面积/色域特征识别每个黄铜块"是什么零件"
② 把「实测质心」与「标称质心」配对，最小二乘解料盘刚体变换 (θ, tx, ty)
③ 第二遍：用变换修正所有槽位 ROI，再算覆盖率与判定
```

**为什么用刚体变换而不是重算单应**：

- 只解 **3 个自由度**，4 个零件给 8 个观测 -> 超定，稳
- **不会把误识别放大成畸变**（单应 8 自由度、4 点恰好定解，一个点错就整体歪）
- 料盘本来就是刚体

**实测验证**（真实画面，故意把标称槽位偏移，看能否找回）：

```
标称偏移 (   0,   0) -> OK 4/4   估计 Δ( -1,  +0)  残差 0.2mm
标称偏移 (+25,   0) -> OK 4/4   估计 Δ(-26,  +0)  残差 0.2mm
标称偏移 (  0, -30) -> OK 4/4   估计 Δ( -0, +30)  残差 0.2mm
标称偏移 (+30, +25) -> OK 4/4   估计 Δ(-31, -25)  残差 0.2mm
标称偏移 (-20, -15) -> OK 4/4   估计 Δ(+19, +15)  残差 0.2mm
```

**偏移多少就报出反向多少，残差恒定 0.2mm。**

**★ 两个必须注意的点**：

1. **旋转矩阵的符号**：图像坐标系 **y 轴向下**，常规数学的 `[[c,-s],[s,c]]`
   在这个坐标系里对应的视觉旋转是 **-θ**。所以 `TrayPose.R` 用 `[[c,s],[-s,c]]`。
   符号写反的症状：模拟料盘转 +7.5°，估计器却报 -7.5°，**残差高达 14.7mm**。
2. **零件被全部拿走时没有基准**（装配完成后）：此时沿用最后一次成功的位姿
   （`pipeline._last_pose` 缓存）。只认到 1 个零件时定不了旋转，只能定平移 ——
   所以缓存只在 `n_used >= 2` 时更新。

**能力边界**：至少认出 2 个零件才能定旋转；1 个只能定平移；0 个则 `ok=False`
（**绝不瞎猜**，退回标称坐标）。认错零件时残差会很大（实测 124mm）自动 `ok=False`。

### 2.9 零件识别：旋转不变的特征向量（不靠固定槽位坐标）

**为什么需要**：只靠"槽位 ROI 覆盖率"判定有个硬前提 —— **料盘位置和朝向固定**。
料盘转一下、相机被碰一下、零件在槽里放歪，ROI 就全错位。

**做法**（`assemvision/core/part_id.py`）：用**旋转不变**的特征向量判定"这是什么零件"，
位置另用 ROI 判。三个判据叠加：`覆盖率` + `特征识别` + `几何形状检查`。

**特征选择原则 —— 只能用转多少度都不变的量**：

| 用 | 特征 | 说明 |
|---|---|---|
| ✅ | `holes` 内孔数 | 拓扑量。轮盘 8+ 孔、底座 1 孔、顶盖 0 孔 —— **最可靠** |
| ✅ | `elongation` 伸长率 | 只用长宽比不用角度。立柱 ~3.2，圆件 ~1.0 |
| ✅ | `area_mm2` 物理面积 | = 像素面积 × mm_per_px²。**区分同为圆形的底座与顶盖的唯一手段** |
| ✅ | `solidity` / `circularity` | 形状比例 |
| ✅ | **色域** `c_hue_mean` / `c_sat_mean` / `c_val_mean` / `c_hue_std` | 颜色天然旋转不变，补材质/氧化差异 |
| ❌ | `rect_angle` | **绝对角度**，料盘一转就变 |
| ❌ | 质心坐标 | 位置另用 ROI 判 |

### 2.10 ★★ 特征稳定性随零件形状而变（立柱是弯曲+锥形+台阶，不是圆柱）

**这是本轮最重要的教训 —— 我曾把稳定性排序搞反了。**

**零件真实形状**（用户手机照片确认）：机加工件，**左端螺纹+法兰 → 锥形过渡 →
长圆柱轴（表面抛光纵向亮纹）→ 右端明显弯折（约 15~20°）→ 细颈+螺纹头+小法兰**。
即 **B（台阶）+ C（锥形）+ E（非回转）** 三种叠加。

**后果**：分割**只切得到圆柱顶面那条高光带**，两侧暗部切不到。所以：

```
长边变化  -1.7%   ✓ 稳（由两端最远点决定，端点永远在）
宽边变化 -30.3%   ✗ 漂（取决于哪条亮纹被切中被切中）
```

**合成实验量化**（合成立柱，只改"被照亮的宽度比例"从 100% 到 40%）：

| 特征 | 相对变化 | 评价 |
|---|---|---|
| `feret` / `rect_long` | **3.9~4.0%** | ✓✓ 最稳（只依赖两端点） |
| `elongation` | 18.0% | ✗ 含宽度因子 |
| `solidity` | **21.0%** | ✗ ★ 见下方警告 |
| `rect_short` | 22.0% | ✗ 含宽度因子 |
| `circularity` | 39.3% | ✗ |
| `area` | **51.5%** | ✗✗ 最不稳 |

**★★ `solidity` 是"圆件上稳、细长弯曲件上不稳"**：

```
圆件（轮盘/底座/顶盖）实测波动  2.2%   ✓
立柱实测波动                   21%    ✗
```

**我一开始拿"跨零件平均波动"（2.2%）当结论，把 `solidity` 当成全局最可靠特征并给了
3.0 权重 —— 那个 2.2% 是拿圆件平均出来的，对立柱恰恰是错的。**
症状：立柱在两次实测间得分 1.00 → 0.48，直接"认不出"。

**解法：逐零件权重**（`PartTemplate.weights`，从 `calibration.yaml` 的
`part_templates.<零件>.weights` 读）：

```
P2_column:  area_mm2 0.1   solidity 0.2   circularity 0.2
            length_mm 4.0  elongation 2.0  short_side_mm 0.5
```

轮盘/底座/顶盖仍用全局默认（`solidity` 是它们的主判据，权重 2.0）。

**新增两个"只依赖端点"的特征**（`features_from_blob`）：

- `length_mm` —— 最长边物理长度。**对细长/弯曲/锥形件唯一可信的特征**，权重 2.5
- `short_side_mm` —— 短边物理长度。圆件上稳（波动 0.4~4%），
  区分顶盖(Ø25) 与底座(Ø65) 一类"同形状不同大小"

**区间半宽也要按"该零件该特征的实测波动"定，不能统一 ±3%**：

```
solidity ±10% | end_width_ratio ±15% | circularity ±25%
elongation ±35% | area_mm2 ±30%（★ 再大轮盘与底座区间会完全重合）
length_mm ±8%  | short_side_mm ±8%
```

> ★ **`solidity`/`circularity` 是比例量，区间上限必须截断到 1.0**
> （算出来 1.056 是物理上不可能的）。
> ★ **立柱的 `elongation` 上限单独放宽到 5.0**：实测 4.74 系高光带导致偏高，
> 而轮盘上限只有 1.36 —— 放宽后仍**互不重叠**（这是它有效的关键）。

**★★ 逐零件权重曾经静默失效**：`checks.py::_classifier()` 建
`PartTemplate` 时**漏传了 `weights`**，所以配置里写死了也不生效。
改这块时务必确认权重真的传进去了（`clf.templates[i].weights` 非空）。

**验证结果**（两组独立实测特征）：

```
旧（统一 ±3% 区间 + 全局权重）: c6第1次 4/4 但本次实测 2/4
                                （立柱 0.48 认不出、底座被认成顶盖 0.90）
新（实测波动定宽 + 逐零件权重）: 两组都是 4/4，得分 1.00
```

**★★ `area` 的归一化踩过三次坑**（`features_from_blob` 里有完整记录）：

1. 用 **bbox 面积** → 圆的"面积/bbox面积"恒为 π/4 ≈ 0.785，**与大小无关**
   → 底座（Ø59.3）和顶盖（Ø19.1）算出来一样大，互相误判。
2. 用 **料盘面积** → 对坐标映射的**尺度**极敏感（同一张合成图在 4.0 与 2.5 px/mm 下
   算出 0.328 与 0.127）→ 底座被判成顶盖。
3. 用 **该槽面积** → 尺度无关、朝向无关，但仍区分不了同为圆形的底座与顶盖
   （各自都填满自己的槽）。
4. ✅ **最终用 `area_mm2`（物理面积）**：实测跨尺度稳定（2.5/4.0 px/mm 下
   4380 / 4377 mm²，差 0.06%）。

**★ 色调 H 是环形量，必须用圆统计**：H∈[0,179] 里 0 和 179 其实相邻，
直接取平均会得到完全错误的值（5° 和 175° 的平均是 90°）。
`color_features()` 把 H 映射到单位圆求平均向量。

**★★ 覆盖率阈值必须按槽缩放**（`check.coverage_scale_by_max`）：

覆盖率 = 零件面积 / 槽面积，**每种零件天生不同**：

```
轮盘 4378mm² / 槽 Ø75     -> 最大约 0.99
底座 3244mm² / 槽 Ø65     -> 最大约 0.98
顶盖  462mm² / 槽 Ø25     -> 最大约 0.94
立柱 1311mm² / 槽 91x28   -> 最大只有 0.51   ★ 细杆 vs 宽胶囊槽
```

用统一的 `coverage_present=0.45` 卡，**立柱完整在位也只有 0.40 → 必然误判存疑**（实测踩过）。
缩放后立柱阈值 ≈ 0.38，完整在位稳过。

**★ 测试朝向鲁棒性时只转轮盘，不要转立柱**：
真实工位里**槽是固定的**，把零件转出槽口范围会被槽壁截断，覆盖率必然下降 ——
那是几何事实，不是"识别不了朝向"。轮盘的**辐条图案**是唯一朝向敏感的特征。
而且要用 `render_scene(wheel_rotate_deg=...)` 做**几何**旋转，
不要用 `warpAffine` 转掩膜（离散网格上的孔洞合并/锯齿伪影会让测试假失败）。

### 2.11 c6 零件特征标定：必须核对"零件有没有放对槽"

**实测真实画面的特征值**（c6 第 1 次，零件均在正确槽位）：

| 零件 | area_mm2 | elongation | circularity | solidity | holes |
|---|---|---|---|---|---|
| P3_wheel 轮盘 | **3265** | 1.01 | 0.47 | 0.79 | 0 |
| P2_column 立柱 | **1074** | **3.36** | 0.46 | 0.90 | 0 |
| P4_cap 顶盖 | **555** | 1.08 | 0.83 | 0.96 | 2 |
| P1_base 底座 | **3155** | 1.11 | 0.79 | 0.96 | 2 |

- **轮盘 3265mm² 反推 Ø64.5mm**，**立柱 1074mm² 反推约 85×12.6mm** ——
  与实物尺寸一致（轮盘 Ø74.4 / 立柱 85×15 在**透视投影 + 分割侵蚀**下略小）。
- ★ **`holes` 在真实画面上的表现与合成图完全不同**：实测是 **轮盘 0 / 立柱 0 / 顶盖 2 / 底座 2**，
  而合成图是 9/0/0/1。说明 `count_holes` 的判据（自适应阈值 + 面积下限）
  在真实光照下数不出轮盘的辐条间孔。**所以不要依赖 holes 区分轮盘**，
  实际区分靠 `elongation`（立柱 3.36 vs 其余 ~1.0）和 `area_mm2`。

**★★ 必须核对零件放对了没有 —— 这是踩过的坑**：
连续跑三次 c6，第 1 次零件摆对（几何自洽），第 2/3 次零件位置全换了
（`P2_column` 变成 `elongation=1.01` 的圆件、`P1_base` 变成 `elongation=6.3` 的细长件），
而脚本**每次都照旧写入 `calibration.yaml`**，把好数据覆盖成垃圾模板。

**★★ 「交叉验证 100%」是假信号，不能作为可信依据**：
那段逻辑是「用刚采的样本造模板 → 用这个模板认同一批样本」，**循环验证必然 ~100%**，
**哪怕零件全放错、哪怕某个槽空着，也照样报 100%**。
它的唯一作用是"检查特征区间有没有互相重叠到认不出来"。

**真正判断零件放对没有，靠「物理尺寸对账」**（c6 的 `采集质量自检` 一节）：
由实测面积反推直径/长宽，与零件的名义尺寸比对。

```
第1次(零件都对)     -> ✓ 通过
   轮盘 实测 圆 Ø64.5mm   应放 槽 Ø75      ✓
   立柱 实测 细长 60x18mm 应放 85x15 细杆   ✓
   顶盖 实测 圆 Ø26.6mm   应放 槽 Ø25      ✓
   底座 实测 圆 Ø63.4mm   应放 槽 Ø65      ✓
第2次(挪位)         -> ★ 拒绝写入（4 项全不符：轮盘位置实测 Ø27、底座位置实测 Ø26…）
第3次(空槽+挪位)    -> ★ 拒绝写入（轮盘槽没采到样本 + 3 项不符）
```

自检不通过时脚本**打印报警并 `return 2`，不写文件**（避免覆盖好数据）。

> ★ **名义尺寸取自 `workpiece.yaml` 的 `slots`，不要用 `radii_mm`**：
> 实测发现 `radii_mm.cap=9.55`（Ø19.1）与 `slots.slot_cap.diameter=25` 自相矛盾，
> 而真实画面量出顶盖 **Ø26.6mm** —— 和槽的 Ø25 吻合，说明 **`radii_mm` 那个值是错的**。
> 容差放宽到直径 [0.55, 1.20] 倍（实测因**透视投影 + 分割侵蚀**会偏小 10~20%）。

重跑前先确认：
- 四类零件按 `slot_wheel=轮盘 / slot_column=立柱 / slot_cap=顶盖 / slot_base=底座` 摆好
- **料盘正放、不要整盘旋转**（槽位坐标是按正放标定的）

> ★ 合成图上的 `test_segment` 现在只判覆盖率、不判零件识别 ——
> 因为合成几何与真实几何差得多（合成轮盘 4377mm² vs 真实 3265mm²），
> 真模板认合成图会"认不出"（分 ~0.3）。**这是 `min_score` 门槛在正确工作**
> （认不准就不猜），不是 bug。

### 2.12 工位全局 ROI：黄铜只在「料盘 + 装配位」范围内检测

**这是 2.2 早就写明该做、直到实测踩到才做的一件事。**

**为什么必须有**（实测真实画面）：木桌的 HSV 与黄铜重叠，**画面顶部的木桌整块被判成黄铜**：

```
实测某帧的连通域:  (认不出) 面积 13269mm²   ← 真零件最大才 3281mm²，4 倍
                  P4_cap   面积  1503mm²   ← 顶盖应是 555，被木桌污染
```

后果：零件识别错（底座被认成轮盘）、面积测量全废、位姿估计算出**荒谬的 48° 旋转**
（而这又触发了 `max_theta_deg` 闸门，见 2.8）。

**为什么不用调阈值**：单独收紧 `h_max`/`s_max` 会削掉零件自己的高光
（实测零件 S 上限 109、H 上限 45，与桌面区间本就重叠）—— 按下葫芦起瓢。
**ROI 是「位置即身份」**，与颜色、光照都无关。

**为什么不用「按固定比例裁掉上下 15%」**：可行，但**余量太薄**：

```
实测料盘底沿到画面 y=376px，"中间 70%" 只到 408px —— 只差 32px
料盘稍微往下挪一点就被切掉
```

而 ROI 外扩 25mm（≈29px）且**跟着位姿补偿一起动**，余量随料盘走。

**实现**（`segment.work_roi_margin_mm`，默认 25mm）：

```
core/segment.py    segment(..., work_roi=mask)  ->  brass_mask &= work_roi
core/checks.py     Qualifier.work_roi_mask()    ->  料盘外扩 + 装配位外扩的并集
                   Qualifier.segment_with_roi() ->  两遍：几何ROI粗分 -> 定位姿 -> 细分
pipeline.py        T3 算 ROI 缓存到 _work_roi，T2 下一帧用它分割
```

**★ 为什么是「两遍」而不是一遍**：ROI 需要位姿（料盘可能被挪动），
而位姿又需要分割结果 —— **先有鸡还是先有蛋**。
解法：第一遍用**几何 ROI**（不依赖位姿）粗分，够用来估位姿；
第二遍用估出的位姿修正 ROI 再细分。
第二遍还有个保护：**只有前景面积没明显变小才采用**（防止 ROI 反而切掉零件）。

**★ pipeline 里 ROI 是"隔一帧"生效的**（T3 算、T2 用）：料盘逐帧变化很慢，
差一帧完全够；而且**宁可"不限制"也不要"限制错"** —— 限制错会把真零件挡在外面。

**写这条的测试时踩的两个坑**（`tests/test_work_roi.py`，都是测试的问题不是 ROI 的）：

1. **合成图画布默认只留 12mm 边距** —— "画布内、ROI 外"的区域几乎不存在，
   于是"放在 ROI 外"的位置其实落在料盘 ROI 里，测不出效果。
   -> 必须用**大边距画布**（`margin_mm=80`）。
2. **只判断"在 ROI 外"还不够** —— 还要确认该处在**不带 ROI 时真的会被切成黄铜**。
   否则放了个空位置（画面外/黑边），前后都是 0，看着像"ROI 没生效"。
   -> 候选点必须**用不带 ROI 的结果筛一遍**。

### 2.13 ★★ 装配体上"数辐条"：为什么要用**金属掩膜**（曾数不出 8 峰）

**症状**：c5 第二步在装配位上数辐条，`spoke_peak_count = 0`（应为 8）。
`--diag` 扫各半径带的峰数：`8~16→0  12~20→0  16~24→0  20~28→5  24~32→3  28~36→1`
**没有任何一条带能数出 8 峰。**

**★ 根因：球头被拍到了，但颜色被绿垫污染，过不了 `h_max=45`。**

沿半径同时量"黄铜占比"和"非绿占比"（非绿 = 不是绿垫 = 有金属）：

```
半径mm   黄铜%   非绿%        ← 关键：黄铜切不到，但"有东西"
  28~30    19.7    72.5
  30~32     4.8    41.4
  32~34     0.5    22.2
  34~36     0.0    16.3       ★ 球头在这里，只是没被切成黄铜
  36~38     0.0    13.0
```

外圈带 28~40mm 里"非绿"占 **27.3%**，其 **H 中值 59、S 中值 85、V 中值 222**。
**那个 `H=59` 是关键** —— 不是"中性白"，是**被绿垫染成淡绿色的金属**
（H 59 紧贴绿垫的 60~100）。球头只有 **Ø5mm**，在 0.86mm/px 下
**只有 6 个像素宽**，边缘抗锯齿后整颗球都被绿垫混色 → 被 `h_max=45` 整条挡掉。
外圈环厚约 2mm = **2.3 像素**，同理。

**★ 解法：`metal_mask`（"亮 + 不是绿垫"，不看色相上限）。**
实测同一帧在 30~35mm 带对比：

```
brass 掩膜:  峰 4   抖动 52.5°
metal 掩膜:  峰 8   抖动  5.9°   [5.5, 57.5, 98.5, 134.8, 176.5, 219.5, 262.0, 310.0]
```

间隔 52/41/36/42/43/43/48/56° → 平均 ~45°，是**真辐条**不是凑数。

**★★ 判据的准确形式（我在这里连续踩了三个坑）**：

```
metal = (v >= v_min) & (s <= s_max) & (~green)
green = (h 在 [g_lo,g_hi]) & (s > g_smin)
```

| 写法 | 漏掉了什么 | 后果 |
|---|---|---|
| 只判 `~green` | **木桌**（H=19,S=122,V=210）色相不在绿区间 → 成了"非绿" | 木桌区 metal 占比 **99.9%**，扫优全废 |
| 加 `V>=v_min` 但仍只判 `~green` | **黑底**（H≈0,S≈0）也是"非绿" | 合成图整幅变金属 → 端到端从 OK 掉成「辐条 0/8」 |
| ✅ 再加 `s<=s_max` | —— | 三种背景都正确 |

`s_max` 实测扫描（木桌区 metal% vs 30~35mm 峰数）：
`200→99.9%/8峰  140→99.3%/8峰  120→44.6%/8峰  100→15.2%/8峰` → 取 **100**。

> ★ **木桌最终是靠 `work_roi` 几何挡掉的（位置即身份）**，
> `s_max` 只是第二道防线 —— 不要把安全性全押在颜色上。

**★ 回落条件是"有没有内容"，不是"是不是 None"**：
绿垫以外的背景（深色底、黑垫）上 metal 判据正确地什么都匹配不到
→ mask 是**全 0 的数组而不是 None**。写成 `is not None` 就会拿空掩膜去数辐条。
判据用 `np.count_nonzero(mask) > 200`。

**★ 装配体上"数臂"也不行**：臂与臂之间的空隙里看到的是下方的底座圆盘
（同样是黄铜），在装配体上用臂的环带数只会得到"整圈都是金属"→ 一个峰都数不出来。
**必须数"球头端伸出外圈的凸起"**。

**★★ 一个容易搞错的点**：`assembly_flags()`（判 `wheel_present` 谓词）
用的是 **`self.r_spoke` = `assembly.radii_mm.spoke_band`（12~24mm）**，门槛 `>= 4`；
而 `check_assembly()`（终检）用的是
**`self.r_spoke_out` = `assembly.radii_mm.spoke_band_outer`（30~35mm）**。
**两个不同的半径带、两个不同的用途**，改的时候别混。

> ★ `spoke_band_outer` 原写 **33~37.5mm**，是**从没验证过的假设值**，
> 落在球头最外沿（~37mm）之外 → 数不出峰。实测应为 **30~35mm**。
> ★ `sweep_band` 原来**只看"峰数 == 8"**，会把**凑出来的 8 个峰**当好的
> （brass 28mm 带是 8 峰但抖动 33°）。现在加了**角度均匀度**判据：
> 间隔相对 360/8 的抖动 > 12° 直接排除。

### 2.14 ★★ 过曝会让**整条判据链静默失效**（不是"少切一点"）

**实测踩过，这是 c5 反复失败的真凶**。曝光 -5.0 在某次工位光照下严重过曝：

```
曝光    过曝%    V均值   brass总px   轮盘那块px
 -3    92.58     254        0            0
 -5     7.96     244     1308          626   ← 轮盘真值约 3200px，只剩 1/5
 -6     0.00     216     9619         3094   ← 正确
 -7     0.00     157     9897         3104
```

**后果链**：

```
过曝 -> 黄铜的色相被推向绿/青 -> 被判成"绿垫" -> 从 metal 掩膜剔除
     -> 装配体上数辐条恒为 0 峰、brass 面积塌到 1/5 -> c5 全线失败
```

**而界面上只是"看着亮一点"**，完全看不出判据已经废了。

**★ 判据：近全白像素（`min(BGR) >= 250`）必须 ≈ 0%。**
`segment.detail` 里会记 `blown_ratio` / `v_mean`，报警阈值取 **0.5%**。
`tools/preview.py` 与 c4/c5 的预览窗口在超阈值时**整屏描红边 + 大字报警**。

**★ 曝光值随环境光变**（`camera.yaml` 的 `exposure_windows.exposure`）：
环境变亮就要往更负调。**换工位、换时段、开/关灯都必须重扫。**
实测某次光照下 -5.0 就过曝，而更早那次 -5.0 是正常的 —— **别以为"上次好用"就永远好用**。

**★ 画面里的高亮区域会把相机测光带偏**：实测画面左侧有一面白墙，
整幅均值被拉到 BGR 217/244/97。**白墙不参与检测，但会毁掉曝光** ——
能挡就挡，或者把测光区域改成 ROI 内（本项目尚未做，暂时靠手动曝光兜）。

### 2.15 ★★ `run_calib.ps1` 是 UTF-16LE，**不要用普通文本编辑器改写**

**实测踩过，后果严重**：用 UTF-8 编辑器改这个文件后，它从 **UTF-16LE + BOM**
变成 **UTF-8 无 BOM**，而 **PowerShell 5.1 读无 BOM 的 UTF-8 会按 ANSI 解码**
→ 中文注释全乱码 → 引号配对错乱 → **脚本直接不可运行**（报"字符串缺少终止符"），
而且**中文内容会实质丢失**：

```
原始: FF FE 23 00 20 00 ...   6740 字节   UTF-16LE + BOM
改后: 23 20 72 75 6E 5F ...   4121 字节   UTF-8 无 BOM   ★ 中文丢了
```

**正确改法**（保持 UTF-16LE）：

```powershell
$t = [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::Unicode)
$t = $t.Replace($old, $new)
[System.IO.File]::WriteAllText($path, $t, [System.Text.Encoding]::Unicode)
```

**★ 如果已经改坏了，`git checkout` 可能修不回来** —— 工作区字节被转码工具动过，
而 git 凭 stat/hash 判断"内容相同"就跳过还原。可靠做法是从 blob 取原始字节，
并**确认前两字节是 `FF FE`**：

```powershell
git cat-file blob "HEAD:assembly_vision/run_calib.ps1" > $tmp
# ★ 必须再校验：$tmp 的字节可能被重定向转码破坏
[System.IO.File]::WriteAllBytes($target, [System.IO.File]::ReadAllBytes($tmp))
```

**★ 改完 `.ps1` 一定要跑一次解析检查**（PowerShell 只在真正执行时才报错，
那时你会以为是"别的地方的问题"）：

```powershell
$t=$null; $e=$null
[System.Management.Automation.Language.Parser]::ParseFile($path, [ref]$t, [ref]$e)
$e.Count   # 应为 0
```

> `.md` / `.py` / `.yaml` 都是 **UTF-8**，用普通编辑器改没问题。
> **只有 `.ps1` 是 UTF-16LE** —— 改之前先确认编码，别一刀切。

| 辐条只判"少"不判"多" | `if spk.count < spk.required` | `spk.ok` 用 `==`，需判多时要用 ok |
| `wheel` 谓词门槛是 4 不是 8 | `out["wheel"] = spk.count >= 4` | 换到"辐条单独成步"的流程时要改成 8 |
| 齐套性不查外圈/轮毂 | `ring_coverage`/`hub_coverage` 算了但没比阈值 | 缺件可能漏判 |
| c4/c5 基线没人读 | `slots.*` 特征运行时不读取 → 合格性只判覆盖率，不判完整性 | `assembly.spoke_peak_count` **已接**（P0-1）；`ring/hub/cap_coverage` **刻意不接**（连缺顶盖都还有 0.874，没区分度，见 6.5） |

### 2.18 ★★ 数辐条：**不能把半径带切成几份投票**（真机"装好了却判缺辐条"）

**症状**（真机 `app.py --windowed`）：轮盘明明完整装好、8 根辐条清晰可见、
界面显示"装配流程全部完成 4/4"，但实际报的是：

```
辐条峰数 0/8        齐套性: NG, 缺失 辐条 5/8
（连续几十帧都是 0~7，**8/8 一次都没出现过**）
```

**★ 根因：`count_spokes` 把半径带切成 `n_radii_bands=3` 个子带各自数峰，
再「取众数、并列时取较小值」** —— 而这个偏置在这里会**稳定地少数**。

实测（真机装配体 `asm_raw.png`，30~35mm 切成 3 带，每带仅 **1.67mm ≈ 1.9px**）：

```
带(mm)        med    p95-med  阈值    峰数
30.0~31.7    0.000   1.000   0.600    8   <- ★ 球头只落在最内侧这个带
31.7~33.3    0.000   1.000   0.600    6
33.3~35.0    0.000   1.000   0.600    5
```

计数 `[8, 6, 5]` —— **三个全不同、没有众数** -> 并列取较小值 -> **5**
-> `5 < required(8)` -> **装好的轮盘被判"缺辐条 5/8"**。

而**同一帧整条 30~35mm 一次数**（c5 的做法）是 **8 峰、抖动 5.9°**。
**两边做法不一致，所以 c5 数出 8、`check_assembly` 数出 5。**

**★ 物理原因**：球头只有 **Ø5mm**，在 0.8623mm/px 下**只有约 6px 宽**，
落进哪个子带**是碰运气** —— 最内侧那个 1.9px 的子带恰好切到了它。

**★ 解法：按「角度均匀度」挑最好的带，而不是让几个带投票取小。**
真辐条的**角度是均布的**，所以"抖动最小"远比"票数最多"可靠：

```
select=vote(旧)     -> count=5  抖动=inf   峰=[98, 135, 177, 262, 309]
select=uniform(新)  -> count=8  抖动=6.2°  峰=[6.2, 57.2, 99, 135, 177, 218, 262, 309]
```

6.2° 与 c5 当初**独立**扫出的基线（抖动 5.9°、峰
`[5.5, 57.5, 98.5, 134.8, 176.5, 219.5, 262, 310]`）几乎逐度吻合 —— **互为独立验证**。

**★ 这个"均匀度"判据不是新发明**：c5 的 `sweep_band` 早就用它
（`真辐条抖动 5.9° vs 凑出来的 8 峰抖动 33°`）。
这次只是把**同一条判据搬到 `check_assembly` 的路径上**，
让两处**用同一个标准** —— 之前它们不一致正是 bug 的温床。

**保留 `select: vote`** 以便对比与回退（`workpiece.yaml` 的 `check.spokes.select`）。
**默认是 `uniform`，不要改回去。**

**★ 兜底不能少**：如果**所有**候选带的抖动都超过 `max_jitter_deg(15°)`，
说明这一圈本来就不规整（真缺辐条 / 被遮挡）——
此时**退回"峰最多"那个**，让缺陷被如实报出来，
而**不是**因为我们挑剔就报成 0（那会变成另一种假 NG）。

**★ 验证**（真机帧上跑完整 `check_assembly`）：

```
修复前: verdict=NG   missing=[辐条 5/8]
修复后: verdict=OK   spoke=8/8  抖动=6.2°  missing=[]
```

而合成图上"少画 0/1/2/4 根 -> 数出 8/7/6/4"**全部仍然准确**，
真缺陷的检出没有因为这次改动而变差。

> ★ 一般教训：**同一个量在两个地方用了两套算法，迟早会打架。**
> c5（标定）与 `check_assembly`（运行）都在数同一批辐条，
> 却一个"整条带一次数"、一个"切 3 带投票"，所以标定时是 8、运行时是 5。
> **标定与运行必须共用同一条判据** —— 这是比这次具体的阈值更重要的结论。

> ★ 另一个教训：**"并列时取较小值（宁少不多）"这类偏置要写清适用条件。**
> 它在"没有真值可依"时是对的（宁可漏报不要误报），
> 但这里我们**有**更强的几何信息（辐条是均布的），
> 这时"取小"就变成了**系统性地少数**。

### 2.19 ★ 零件识别用的是什么方法、准确率多少（可复现的量化）

**方法：旋转不变的特征向量 + 区间匹配 + 加权打分。没有神经网络。**

```
features_from_blob(blob)  ->  特征字典
PartTemplate.score(feats) ->  (总分, 各特征得分)      # 区间匹配 _band_score
PartClassifier.classify() ->  (part, score, detail)   # 取最高分；< min_score 则返回 None("认不出")
```

**判据三层叠加**（缺一不可，`check_slots` 里）：
1. **覆盖率**（位置即身份）——该槽里有没有东西
2. **特征识别**（本节）——那东西是什么零件
3. **几何形状检查**——形状自洽（如立柱的细长比）

**特征清单**（`calibration.yaml` 的 `part_templates.*.ranges`，由 `c6` 标定产出）：
`circularity / solidity / elongation / holes / end_width_ratio / aspect /
area_mm2 / area_frac / c_hue_mean / c_hue_std / c_sat_mean / c_val_mean /
c_sat_hi_frac / length_mm / short_side_mm`

**全局特征权重**（`calibration.yaml` 的 `part_id.feature_weights`）：
`holes 2.0 / elongation 2.0 / area_mm2 1.8 / solidity 1.5 / c_hue_mean 1.4 /
circularity 1.2 / c_sat_mean 1.0 / end_width_ratio 1.0 / ...`
**逐零件权重**覆盖全局（目前只有立柱有，见 §2.10）。

#### 实测：合成序列端到端（精确真值）

工具：`python tools/measure_part_id_e2e.py`（真值来自槽位几何，与分类器无关）

```

FN 漏检       = 3      FP 误检         = 0
★ 准确率 (TP+TN)/全部 = 177/180 = 98.3%
★ 召回率（有件时认对） = 75.0%      ← ★ 这个才是有意义的那个数
★ 精确率（认对/所有认出）= 100.0%   ← 零误检
```

> ★ **98.3% 这个数被"168 个空槽正确地空着"抬高了** ——
> 报告准确率时**必须同时给召回率与精确率**，否则会误导。
> **零误检（FP=0）比高准确率更重要**：宁可说"认不出"，也不要认错。

3 个漏检的明细：`f009~f011`，轮盘槽里那个零件被认成 `P1_base`。
**根因是合成图自己的几何问题**（见下），不是分类器：

```
make_synthetic.SLOTS 的槽心  vs  workpiece.yaml 的标称槽心：
   P3_wheel   Δ=(-4.60, +3.50)   距离  5.78 mm
   P2_column  Δ=(-3.20,+10.30)   距离 10.79 mm
   P4_cap     Δ=(-6.00, +3.20)   距离  6.80 mm
   P1_base    Δ=(-9.50, +0.60)   距离  9.52 mm
```

**判据**：拿**渲染真值**直接解位姿也报 `θ=-2.02° / 残差 3.1mm`；
把合成槽心当标称再解一次就是 `θ=+0.00° / 残差 0.0mm`。
-> **那 ~2° 与 ~3mm 完全来自"合成几何 vs 标称几何"的不一致**，
与估计器、与分割都无关。

> ★ **合成序列不能当"真机准确率"用** —— 它测的是**判据正确性**。
> 真机准确率只能在真机上现跑（`--live`，用「零件落在哪个槽」当真值）。

#### 实测：料盘旋转 / 平移检测能力

工具：`python tools/measure_rotation.py`（直接喂已知真值的质心，无渲染/分割噪声）

   1 件（只剩底座）    ok=True    θ=+0.00° —— **只定平移，旋转定不了**（有偏）

> 它证明的是**解算器实现正确**（能精确解回它自己应用的变换），
> **不构成"真机旋转精度"的结论**。真机旋转精度要在真机上测。

#### ★★ 两个"我测错过"的教训（别重犯）

1. **`render_scene(wheel_rotate_deg=...)` 转的是"辐条图案"，不是料盘。**

   会得到"θ 恒为 -2.0°、与真值完全无关"这种自相矛盾的表格。
   同理 `rotate_deg` 转的是**立柱**（源码自己注明是"研究几何用"）。
2. **改用"整幅图几何旋转"之后又被合成几何的 5.8~10.8mm 偏差污染。**
   于是凭空多出 ~2°/3mm 的固定偏差。

   -> **测一个纯几何算法，就直接喂它输入**（质心），
      不要在它外面套一层"渲染 + 分割"再声称测的是它。

### 2.20 ★★ 零件实时检测 + 追踪 + 遮挡处理（含三个真 bug）

用户要求：「写一份测试代码，要能让我看到实时画面、看到**形状轮廓而不是方框**；
戴蓝手套拿起来就算遮一部分也要能认；帧率要高；要去抖；用卡尔曼/KCF 等追踪算法；
**要能延伸到树莓派**。」

#### 为什么必须"检测 + 追踪"，不能每帧全图分割

实测耗时（PC / 树莓派 4B 按 **6×** 估）：

```
全图分割 640×480    9.88 ms  /  ≈59 ms   <- 每帧都跑的话 Pi 上限只有 17fps
追踪器 update：MOSSE       0.25 ms /   2 ms   ★ 树莓派推荐
              MedianFlow   1.83 ms /  11 ms
              KCF          2.01 ms /  12 ms   ★ PC 默认
              CSRT        22.72 ms / 136 ms   ★ 千万别在 Pi 上用
```

**做法**：每 N 帧才全图分割，其余帧只跑追踪器。
实测 `--detect-every 5`：**PC 57~67 fps**，每帧均摊 **11 ms**（Pi 估）-> **≈95 fps**。

★ **一个反直觉的结论**：`kcf / mosse / medianflow` 三种后端的帧率**几乎一样**
（都是 11 ms/帧）—— 因为**瓶颈已经完全变成分割**，追踪器已经不是瓶颈了。
所以后端选择该按**精度/稳定性**选，不用纠结速度。

#### ★★ 三个真 bug（都是实测暴露的，不是理论）

**bug 1：`visible_ratio` 恒为 1.0（我第一版写反了语句顺序）**

```python
# ✗ 错：先更新参考值，再算比值 -> 参考值被"遮挡后的小面积"拉低 -> 比值恒为 1
if vis >= self.full_ratio:
    t.area_ref = (1-rate)*t.area_ref + rate*a
t.visible_ratio = a / t.area_ref

# ✓ 对：先用**旧**参考算比值，再按状态决定要不要更新参考
vis = a / max(1e-6, t.area_ref)
...
if vis >= self.full_ratio:
    t.area_ref = min(ema, t.area_ref * (1.0 + rate))   # 只允许缓慢上升/有限下降
```

**后果不是"数字难看"，而是判据失效**：`visible_ratio` 恒为 1
-> 状态永远是 `detected` -> **每帧都拿"被切掉一半的残缺件"去重新识别** -> 认错。
实测：遮挡 50% 时 `P3_wheel` 被认成 `P2_column`。

**bug 2：`score_ema` 没被初始化，导致"换标签闸门"形同虚设**

新建轨迹那条分支**直接赋值** `t.part_id, t.id_score`，没走 `apply_id()`，
于是 `score_ema` 恒为 **0** —— 后续"新标签要比现有分数高 `id_margin`"的闸门
**永远为真**，任何标签都能顶掉现有身份（实测第二次识别就把 `P_A` 换成了 `P_B`）。
修法：新目标也必须走 `apply_id()`。

**bug 3：完全遮挡时 `visible_ratio` 不降**

追踪器 `update` 失败（目标被手套**完全盖死**）时，旧代码只更新位置、
**不动可见度** -> 界面一直显示「可见 100%」（实测：85% 遮挡时仍显示 100%）。
修法：`update` 失败就把 `visible_ratio` 置 0 并进 `occluded`。
★ 且 `lost_frames` 的**清零只由"真的看到检测"负责** —— 不要在 `ok=True` 时清零：
追踪器在完全遮挡时也可能报 ok，那样计数永远涨不上去、状态就降不下来。

#### ★★ 三个"我测错了"的教训（比 bug 本身更值得记）

1. **测遮挡时对每个遮挡度都新建追踪器** -> 那是"新目标"，
   参考面积 = 当前面积 -> `visible_ratio` 恒为 1.0，**测出来的结论是假的**。
   真实场景是「**先看见完整零件，手才遮上来**」—— 测试必须按这个时序（先喂几帧满面积）。
2. **选块用"取面积最大"是错的**：遮挡到只剩一点点时，目标块的面积会**小于**
   追踪框里混进来的别的零件 -> 选中错的对象（实测 85% 时选中质心距 **87px** 的另一块）。
   正确做法：**按"离预测位置最近"选**，并设一个距离上限。
3. **中文串里嵌半角引号**又一次 `SyntaxError`（本项目已踩多次，见 §6 约定）。
   用 `「」`。

#### 实测：遮挡下的可见轮廓（这是"遮一部分也能认"的依据）

`tools/part_track_occlusion_test.py`，真机帧 + 人工叠加手套色矩形：

#### 遮挡处理的三档策略（**取舍是有意的**）

```
visible >= full_ratio(0.80)         -> detected  正常：**重新识别身份**
occluded_ratio <= v < full_ratio    -> tracked   只更新位置/轮廓，**身份沿用**
v <= occluded_ratio(0.55)           -> occluded  **冻结身份**，绝不重判
```

★ **为什么遮挡时坚决不重判身份**：残缺件的面积/长度/长宽比全都变了，
拿去认必然出错（实测底座被切到 1542mm² 时曾被认成轮盘，见 §2.19）。
再加两道闸门：**换标签要有分数余量**（`id_margin`）、**形状失真时直接冻结**
（`aspect` 偏离 1 太多说明被遮成细条，此时"像柱状物"是假象）。

#### 卡尔曼参数是**扫参**定的，不是猜的

场景 = 真值匀速直线 + 观测噪声 sigma=3px（贴近"分割质心抖动"）：

```
process/meas        轨迹误差(原)  轨迹误差(滤后)   逐帧抖动(原)  逐帧抖动(滤后)
0.03 / 0.12（旧）      2.312       1.930          2.902        1.958
1e-3 / 3.0（现）       2.312       1.286          2.902        1.044   ★ 降 44%
```

参数含义（调参按这个想）：`process_noise` = 多信模型预测，`meas_noise` = 多信观测。
零件帧间几乎不动（料盘是静的、手慢）-> `process_noise` 应**很小**；
分割质心抖动是 1~3px -> `meas_noise` 与之同量级。

★ **测试指标也要选对**：第一版测的是「逐帧位移的起伏」，那个指标是**错的** ——
正常工作的卡尔曼在跟匀速目标时位移本就接近真值。该看的是**离真值的误差**。

  `make_tracker()` 会真去构造一次（不是只看属性在不在 —— 实测 5.0 里
  `cv2.TrackerKCF` 存在但直接构造会抛异常）。
- 后端实测表见上；**Pi 推荐 `mosse`**，`csrt` 不要用。
- `detect_every_n` 在 Pi 上建议 **8~10**（PC 3~5）。
- 全部 numpy/OpenCV，**无新依赖**。

### 2.21 ★★ 追踪后端实测：只有 KCF 可靠（别按"常见做法"选）

**背景**：用户真机实跑 `tools/part_track_demo.py`，报「**处理帧数 0**」。
顺着查下去，暴露出**一串**实测结论，全部与"常见做法"相反。

#### bug：真机一帧都处理不了（demo 漏了 `open()`）

```
UvcStereoSource.__init__ 只设 self.cap = None，**不自动开相机**
read() 里第一句就是 `if self.cap is None: return None`
-> 第一帧读到 None -> 我的循环 `if frame is None: break` -> **0 帧退出**
```

`pipeline.py` 第 145 行就是 `self.source.open()` —— **照它做**。
另外 `make_source` 的真实签名是 `(cam_cfg, source, path)`，
我第一版往 `cam.data["capture"]["kind"]` 里塞值是**臆造的字段**，不生效。

**★ 第二个错**：真机 `read()` 返回 None 多是**预热/偶发丢帧**（DSHOW 开流要几帧），
**不能当成"序列结束"** —— 那是图片序列的语义。两者必须分开处理。

#### ★★ 后端实测表（PC，640×480）

| 后端 | 单次 update | 结论 |
|---|---|---|
| **kcf** | **5.5 ms** | ★ **唯一可靠**，默认。4 目标约 32ms/帧 |
| mosse | 0.02 ms | ✗ **`update` 恒返回 False**（OpenCV 已知问题）—— 实测 **40/40 全"丢"**，没法用 |
| medianflow | 1.8 ms | ✗ **会崩**：`lkpyramid` 断言 `prevPyr.size() == nextPyr.size()`（LK 光流要求前后帧尺寸一致） |
| csrt | 22.7 ms | ✗ 太慢（Pi 估 136ms） |

**★ MOSSE 的失败方式很危险**：它 `update` 返回 `False` 却**仍在跟**。
如果用 `ok` 判断，会以为"全丢"；如果不看 `ok`，又会用到它没校准的结果。
**两种用法都错**，所以直接不用。

#### `segment` 的耗时与 ROI 大小**几乎无关**

```
segment(全图 640x480)        10.52 ms
segment(全图 + work_roi)      9.95 ms
segment(小 ROI 100x100)       8.90 ms   ← 只省 15%
```

-> **"给小 ROI 就快"是错的**。耗时在**整幅 HSV 转换**那一步，
所以"用追踪框当 ROI 重新分割"（遮挡路径）省不了多少时间 ——
它的价值在**正确性**（拿到可见部分的轮廓），不在速度。

#### ★★ 试过并**放弃**的方案：裁剪小图再跑 KCF

推理依据（这条推理本身是对的）：KCF 耗时**随搜索窗而非帧尺寸**增长 ——

```
只改框大小（同帧同 API）:
   40x40   4.7 ms      120x120  10.3 ms
   80x80  15.8 ms      320x320  56.2 ms
```

**实测结果：只快 14%，但精度崩了。**

```
                 _run_trackers中位ms   静止漂移px   跟移动误差px
整帧（旧）            33.51            2.76         0.75
裁剪 pad=40px        29.50          131.46        10.53   ← 漂移 2.76 -> 131px
裁剪 pad=24px        29.26          131.46        10.53
```

**原因**：裁剪窗会随目标移动而滑动，偏移一变就得**重新 `init`**，
而 `init` 既不快、又**破坏追踪器的内部状态**。
-> **已放弃，代码已完全回退**（不留半成品）。

> ★ 教训：**推理对 ≠ 实测对。** "搜索窗决定耗时"是对的，
> 但由此推出的"裁剪就能加速"忽略了**裁剪窗自身会滑动**这个副作用。
> **先量收益与精度，再决定留不留。**

#### 调大 `--detect-every` **几乎不提帧率**（反直觉）

真机实测（120 帧，4 个零件）：

```
detect-every  中位fps  追踪update  分割/周期   每帧均摊
      3        26.1     31.72ms    2.96ms     34.67ms
      5        27.9     36.09ms    1.79ms     37.88ms
      8        28.1     31.08ms    1.12ms     32.20ms   ← 实测最好，已设为默认
     12        29.1     35.31ms    0.74ms     36.05ms
```

**因为分割早已不是瓶颈**（摊薄后只剩 0.7~3ms），
**瓶颈完全是 KCF 的"每目标固定成本"**（4 件 × ~8ms）。

-> **想提帧率只能少跟几帧，不是换后端、也不是省分割。**

#### 最终真机结果

```
帧率（中位）  : 28.9 fps   （相机上限 31 fps -> 已 93%）
稳态范围     : 20.9 ~ 31.9 fps
每帧均摊     : 31.91 ms -> 上限 31.3 fps   ✓ 够用
退出码       = 0（离线 / 窗口 / 端到端三条路径都验过）
```

#### ★★ 报帧率必须用**中位**，不能用均值

同一个真机运行：**均值 8.5 fps、中位 28.9 fps** ——
因为 DSHOW 开流要预热，前几帧很慢，**均值被那几个慢帧拖垮**。
第一版只报均值，**看着像"只有 7fps"，其实已经贴着相机上限**。
=> 报帧率**剔掉前 10 帧、报中位**；均值只作参考。

#### ★ 离线基准的输入必须真的产生目标

早期离线 `--bench` 报「追踪 update/帧 **0.01ms**」—— 那是**假数据**：
合成序列的零件面积 > `max_area_px(8000)`，**全被过滤掉，追踪器手上一个目标都没有**。
真机有真零件，KCF 每帧要 30ms。

> ★ 教训：**基准测试要先确认"被测对象真的在干活"**，
> 否则测的是空循环，还会得出"性能很好"的错误结论。

### 2.22 手（蓝手套）方框检测 —— 「零件画轮廓，手画方框」

**用户要求**：「还要能识别工人的手，工人的手用方框框就可以了（戴蓝手套）」
以及「如果被手遮挡只需要描出没被遮挡部分的轮廓就行」。

#### 为什么两者画法**刻意不同**

| | 画什么 | 为什么 |
|---|---|---|
| **零件** | **形状轮廓**（`drawContours` + 顶点） | 零件是刚体、形状是它的身份特征；轮廓能直接看出「被遮了多少」 |
| **手** | **方框**（`rectangle` + 四角加粗） | 手是非刚体、形状多变，画轮廓既不准也没意义；下游要的只是「手在哪、有没有压到某个槽」 |

#### 实测踩到的坑：`hand_on` 不是 `segment()` 填的

```python
res = seg.segment(frame, ...)
res.hand_on        # 永远是空字典 {}
```

`Segmenter.segment()` **只填** `glove_mask` / `glove_bbox` / `glove_area_px`，
**不填 `hand_on`** —— 它是 `pipeline.py` 另调一次算的：

```python
# pipeline.py:219
seg.hand_on = glove_hits(seg.glove_mask, <槽位多边形>, thresh)
```

所以工具里要**照 pipeline 的做法自己调 `glove_hits`**，
否则「手压在哪个槽」永远不显示。

#### 手套分割已有的过滤（配置在 `workpiece.yaml` 的 `segment.glove`）

```yaml
h_min: 95   h_max: 130      # 蓝手套色相
s_min: 80   v_min: 130      # v_min 是关键：键盘背光/屏幕与手套色相重叠，
                            #   只能靠亮度下限分开（见实录 2.3）
min_area_px: 3000           # 小于此不算手（滤噪声）
max_area_px: 200000         # 大于此不算手
max_aspect: 6.0             # 太细长不算手
```

实测（`tools/check_hand_box.py`，合成手套）：

```
用例            手套px    glove_bbox        手框   压在
方块 90x70       6298    (330,200,91,71)   OK    wheel
方块 140x110    15398    (300,180,141,111) OK    wheel
方块 200x150    29998    (280,170,201,151) OK    wheel
细长 260x60     15598    (250,300,261,61)  OK    cap,base
小 40x40            0    None              --    （被 min_area_px 正确滤掉）
```

> 我预告过「细长 260x60 会被 `max_aspect=6.0` 过滤」—— **实测没被过滤**：
> 261/61 = **4.28 < 6.0**，所以正常检出。**我的预测错了，实测对了。**
> 教训同 §2.21：**先量，别推。**

#### 「手: 无」不等于「画框没生效」

真机录了 90 帧去找手框，**一帧都没有** —— 因为那 90 帧画面里**本来就没有手**
（四个零件都在槽里）。这和「画框代码没生效」在日志上**长得一模一样**。
-> 所以必须用**合成的可控手套**单独验证渲染，
不能拿「真机没看到框」当结论（`tools/check_hand_box.py` 就是干这个的）。

#### 手只在**检测帧**算一次

`_mask()` 要跑 HSV + 连通域（几个 ms），所以手和零件共用同一个检测节奏
（每 `detect_every_n` 帧），非检测帧沿用上一帧的手位 —— 手移动慢，够用。

### 2.23 手（手套）明明在画面里却显示「手: 无」—— `min_area_px` 与形态学核的量级错配

**症状**（用户真机截图）：手（蓝手套）清楚地在画面里压着料盘，
面板却显示 `手: 无`；而同一次运行 `遮挡 100%` 是**正确**的。

#### 根因：手指**碎成多块**，每块都过不了 `min_area_px`

在真实 640×480 下量手套掩膜的**未过滤**连通域：

```
[(613, 1.33), (502, 2.04), (383, 1.29), (278, 1.27)]      <- (面积, 长宽比)
```

**手指碎成 4~5 块，没有一块超过 `min_area_px = 3000`** ->
整只手被滤掉 -> `glove_bbox = None` -> 界面显示「手: 无」。

而 **`glove_mask` 本身没有被清空** —— 所以 **`hand_on` 与遮挡判定一直是正确的**，
**只有显示受影响**。这就是「`遮挡 100%` 对、但 `手: 无`」的原因。

#### 关键：`min_area_px` 过滤的只是「用于显示的那一个 blob」

```
Segmenter.segment():
    res.glove_mask   = 完整的手套掩膜        <- hand_on / 遮挡判定用它（一直没问题）
    res.glove_bbox   = **过滤后最大的那一个 blob**  <- 显示用它（被滤掉 -> None）
```

**两个字段的生命周期不同**，所以会出现"判定对、显示错"这种**看着自相矛盾**的现象。

#### 修法：先让手指连成一块，再定闸门（两步，缺一不可）

闭运算核扫描（有手帧的最大块面积 / 块数）：

```
闭运算核    最大块面积   块数        说明
(不闭)        450       3 块
5            638       4 块     <- **原配置，仍然是碎的**
9           2225       2 块
15          2629       2 块
21          3219       2 块     <- 连成一块，且不过头
31          6399       1 块     <- 连得过头（会把周边并进来）
```

-> 取 **`morph_close: 21`** + **`min_area_px: 2000`**
（有手最大块 3219，是闸门的 **1.6 倍**；6 个无手帧的未过滤最大蓝块**全部 = 0px**，
所以 2000 仍绰绰有余）。

#### ★★ `3000` 这个值没错，是**用法变了**

| 时期 | 场景 | 真手套面积 | 当时定的闸门 |
|---|---|---|---|
| 早期（§2.3） | **整只手** + 笔记本键盘背光干扰 | 83316 px | 3000（挡 7882px 的假蓝块） |
| 现在 | **几根手指**搭在料盘上 | 最大块 **613 px**（碎块） | 3000 -> **整只漏掉** |

> ★ 教训：**一个阈值只在它被测出来的那个场景里有效。**
> 用法一变（整只手 -> 几根手指），同一个数字就从"合适"变成"全漏"，
> 而配置里那句"依据实测"的注释**还在那儿**，看着毫无问题。

#### ★ 我在这条上差点又犯错

第一次量到"最大块 613"时，我准备直接把 `min_area_px` 降到 600。
**但 613 是"最大的一块"，不是"整只手"** —— 整只手要 4~5 块的**面积和**。
只降阈值会在"手指分得更碎"时再次失效；
**真正的问题是碎块，所以要先闭运算把它们连起来。**

> ★ 与 §2.21 同一条教训：**先看清量的是什么，再动手改。**

#### 验证

```
有手帧（用户截图，缩到 640 宽）: glove_area = 3092 px  bbox = (561,425,79,74)  -> DETECTED
6 张无手真机帧              : glove_area = 0     bbox = None                  -> 无误检
工具: tools/verify_glove_fix.py  -> PASS
```

#### ★ 一个**不要**被误导的发现

拿用户截图（**窗口截图**，含标题栏 + 62px 面板）去和相机坐标的槽位多边形对账，
会发现"手一个槽都没压上"（overlap = 0）。**那是坐标错位，不是 bug** ——
窗口截图的内容被下移了约 62px，与 640×480 的相机帧不是同一个取景。
**别拿窗口截图当相机帧做几何对账。**

### 2.24 ★★ 「完全被遮住」算**遮挡**还是**丢失**？—— 状态机的时长阈值定错了

**用户指出**（原话）：

> 刚刚手还把底座完全挡住了，这里就有个问题被全部遮挡应该算遮挡还是丢失。
> 但很显然我没有动底座应该算作遮挡。只有当遮挡物全部移开之后或者手，
> 如果屏幕里面没有任何该零件的一小部分才应该算作丢失。

**原来的实现是错的**：

```python
t.state = "occluded" if t.lost_frames <= self.max_lost else "lost"    # max_lost = 12
```

`max_lost_frames = 12` 帧 ≈ **0.4 秒**。而零件**完全被手挡住**时追踪器 `update`
必然失败 —— 于是 **手搭上去半秒就报「丢失」，哪怕零件一动没动**。
紧接着 `_prune()` 会把轨迹**删掉**，`_last_pose` 缓存与"它应该在哪"就都没了。

#### 正确语义（三档，而不是两档）

| 状态 | 含义 | 判据 |
|---|---|---|
| `occluded` | 零件**还在原位**，只是被挡住（**含完全被挡**） | 追踪失败，但时长 < `max_occluded_frames` |
| `lost` | **久到可疑**，可能真被拿走了 —— **但仍不删** | 时长 >= `max_occluded`，< `max_lost` |
| `gone` | 已经放弃（超出 `max_lost` 才允许清掉） | 时长 >= `max_lost_frames` |

```yaml
tracking:
  max_occluded_frames: 150   # 约 5 秒：仍认为"在，只是被挡"
  max_lost_frames: 300       # 约 10 秒：再久才升级为"可能被拿走"（**仍不删**）
```

#### ★ 为什么 `lost` **也不能删**

删了它，就丢掉了"它本来应该在哪"这条信息。而**手一移开、零件重新露出来时，
本该能立刻恢复**（`_adopt` 会按 IoU / 距离重新关联上，身份也还在）。
只有到 `gone` 才真清掉。

实测这条恢复链路是通的：

```
连续 10 帧完全不可见  -> occluded   （身份 P_KEEP 保留、轨迹不删）
遮到 25 帧            -> lost       （仍不删）
手移开                -> detected   ★ 恢复成功，身份还在
再遮 45 帧            -> 才允许清理
```

#### ★ 教训：**状态机的"时长"参数，语义必须先定清再选数字**

`12` 这个数字本身没问题 —— 它回答的是"追踪框连丢几帧就当它没了"，
用在"快速剔除误检"上很合理。**但用户要的是另一件事**：
「没动过的零件被挡住 ≠ 零件不在了」。

**同一个计数器被两种语义抢用**，所以怎么调都不对：
调小了手一挡就报丢，调大了真拿走也不报。
-> 拆成**两个阈值 + 三个状态**，各管一件事。

### 2.25 ★★ 「丢失」的正确定义：**遮挡物移开后**全图搜 2 秒仍无果

**用户纠正了我的第二版实现**（原话）：

> 不是持续很久才被怀疑，而是最后一次还检测到有零件的位置的时候，
> 到**遮挡物已经完全消失了之后的一小段时间（暂定2秒）**还是没有检测到这个零件，
> 算作这个零件丢失。而且找这个零件是**全图搜索**而不是范围搜索。

#### 我连着错了两次

| 版本 | 判据 | 错在哪 |
|---|---|---|
| 第 1 版 | 追踪失败 12 帧（0.4 秒）就 `lost` | **手搭上半秒就报「丢失」**，零件一动没动 |
| 第 2 版 | 追踪失败 150 帧（5 秒）才 `lost` | **计时起错了** —— 从「看不见」开始算，而应该**从「遮挡物移开」开始算** |
| **第 3 版（现行）** | 遮挡物移开后，`lost_grace_frames`(60 帧≈2 秒) 内**全图搜**不到 -> `lost` | —— |

**关键差别**：第 2 版里手一直挡着也会往 `lost` 走（因为只数「看不见的帧数」）。
而正确语义是 —— **手还盖着的时候永远不算丢**（挡多久都不算，零件没动）；
计时器只在**遮挡物完全移开**那一刻才启动。

#### 三段逻辑（`PartTracker.judge_lost`）

```
① 遮挡物还盖着      -> occluded，**永不判丢**（挡多久都不算）
② 遮挡物刚移开      -> 启动 clear_frames，窗口内做**全图搜索**
③ 窗口(2秒)过期仍找不到 -> lost；再过 3 倍 -> gone（允许清理）
```

配置：`tracking.lost_grace_frames: 60`（30fps 下 ≈ 2 秒）、`cover_overlap_ratio: 0.25`

#### ★ 「全图搜索」是硬要求，不是措辞

判据里的 `seen_ids` **必须来自覆盖全画面的检测**。
如果只用工位 ROI 内的那一份，就退化成「范围搜索」，零件被挪到 ROI 外时永远找不到。
-> demo 里每隔 `--full-search-every`（默认 30 帧 ≈ 1 秒）跑一次**不带 work_roi** 的全图分割，
专门供判丢用。（全图比带 ROI 略贵：8.9 vs 10.5ms，所以控制频率。）

#### ★ 踩到的两个「新建路径又漏了」的坑（与 §2.20 的 `score_ema` 同一类）

1. **`ever_seen` 在新建轨迹时没置位** —— `_detect` 的「新目标」分支漏了它，
   于是 `judge_lost()` 把每条轨迹都当成「一次都没看到过的误检」直接清掉，
   表现是**轨迹莫名消失、判丢逻辑完全不生效**。
2. **`judge_lost` 无条件覆盖状态** —— 一个**刚刚正常检测到**的目标
   也被改写成 `occluded`（遮挡对照图里「完全可见 0%」也变橙）。

### 2.27 ★★ 幽灵轨迹（重复轨迹）+ 缺件不报

**用户反馈**（两张真机截图）：

> 图1「零件 5（可用 3 / 遮挡 2）」：底座位置是空的，
> 但右下画着一个形状扭曲的橙色三角形、标「全图搜 1帧」；
> 而且**底座没报缺件**。
> 图2「零件 8（可用 4 / 遮挡 4）」：4 个绿色正常 + 4 个橙色幽灵，
> 幽灵都在料盘外。

#### 根因 1：幽灵轨迹 = 匹配用了「预测位置」+ 贪心认领

三个缺陷叠加在一起：

| # | 缺陷 | 后果 |
|---|---|---|
| ① | 匹配用的是 **卡尔曼预测位置** `t.centroid`（追踪失败后会**漂移**），配上宽松的 `dist_match_px=40` | 一条轨迹**抢到别处的块** -> 那个块本该新建却没有 -> 轨迹数虚增/错配 |
| ② | 匹配是「**按列表顺序贪心**」 | 先遍历到的轨迹抢走后一条更该拿的块 |
| ③ | `visible_ratio == 0` 时仍**照画旧 `contour`** | 那就是那些**扭曲三角形** |

**修法**：
1. 匹配改用 `last_centroid` / `last_bbox`
   （**最后一次真正检测到**的位置，而不是预测值）；
2. **全局最优认领** —— 所有 (轨迹, 块) 配对按打分排序，
   从高到低依次认领，**每条轨迹与每个块都只能用一次**；
3. 不可见时**不画轮廓**，改画空心圈 + 放射线
   （明确表示「记忆位置，非当前观测」）。

#### 根因 2：缺件判据用了「有没有轨迹落在槽里」

```python
# ✗ 旧：幽灵轨迹正好压在底座上 -> 被当成"有件"
missing = [k for k, v in slot_polys.items()
           if not any(t.part_id and _id_in_slot(t, v) for t in tracks)]
```

**正确的假设是「全图检测说有才有」**，不是「轨迹在那儿」：

```python
# ✓ 新：用全图检测的权威结果 seen_ids
if seen_ids is not None:
    last_seen_ids = set(seen_ids)
    last_missing = [k for k, part in slot_parts.items() if part not in last_seen_ids]
```

★ 没跑全图搜索的帧沿用上一次结果，避免「缺件」提示闪烁。

> ★ 教训：**「某个东西在不在」要用检测结果判，不要用追踪状态推。**
> 追踪状态是「我记得它在那儿」，而检测结果才是「我看见它了」。

#### 顺带修的开销问题

加上全图搜索后每帧均摊从 32ms 涨到 **40ms**（掉帧）。定位到两处：

1. 全图搜索里跑了 `check_slots`（覆盖率 + 特征 + 逐槽判定）——
   而判丢只需要「哪些零件 id 可见」。
   -> 改成**直接对全图分割出的块做识别**（只认面积像零件的）：**39.8 -> 34.4ms**。
2. 长时间看不见的轨迹仍在跑 KCF（每目标约 8ms）。
   -> `lost_frames > lost_grace_frames` 时**跳过 KCF**，只保留卡尔更预测。

结果：真机中位 **27~28 fps**（相机上限 31）。

#### ★ 测试里又一个「构造不成立」

第一版「一个块只能被一条轨迹认领」的测试，把两条轨迹放在 **60px** 间距，
而 `dist_match_px` 恰好是 60 —— 于是它们**自己被合成了一条**，测试直接失败。
-> 必须先用小 `dist_match` 建两条，**再放宽** `dist_match` 让它们都够得着同一块。

> ★ 与 §2.21/§2.25 同一条：**测试构造本身就是一个宅判据，先验证它成立。**

### 2.28 ★★ 幽灵在「黑色料盘外」且是「全图搜 0 帧」—— 两道闸都漏了

**用户定位**：「幽灵是黑色料盘外的全图搜 0 帧」

#### 「0 帧」就是诊断结果

`全图搜 0帧` 意味着**这条轨迹刚建出来就从来没跟住过任何东西**
—— 它是**从噪声里生出来的轨迹**。而「料盘外」告诉我们它在哪里。

#### 为什么两道闸都没拦住

| 闸 | 为什么失效 |
|---|---|
| 第一道：位置（`work_roi` 内） | ★★ `work_roi` 本身是料盘**外扩 25mm** 的 —— 料盘边沿外仍有一条在 ROI 内，噪声就在那里 |
| 第二道：该块能不能被认成零件 | 当时**根本没有这道闸** |

#### 实测（`tools/verify_allow_new.py`，真机帧）

```
assembly_choice.png
   4026 (351,252)  inROI=yes  P3_wheel   0.70  ALLOW
   3998 (441,340)  inROI=yes  P1_base    0.77  ALLOW
   1197 (441,253)  inROI=yes  P2_column  0.84  ALLOW
    668 (346,343)  inROI=yes  P4_cap     0.97  ALLOW      -> 4/4 真零件全放行

now_raw.png
    600 (610,474)  inROI=NO   P2_column  0.89  reject     ★ 就是它！
```

**最后一行就是用户报的那个**：料盘外一个 600px 的块，
**连分类器都骗过了（认成 P2_column 得分 0.89）** ——
只有**位置闸**能挡住它。这也是用户说「其他颜色相近的也被弄成丢失」的真相。

#### 修法：两道闸 + 一处不一致

1. **位置闸要先内缩**（`--allow-new-inset-px`，默认 6）：
   只判「在外扩 ROI 内」挡不住料盘外的噪声。
   实测内缩 6px 后覆盖 24.8% -> 22.5%，**四个真零件仍全在内**。
2. **新建轨迹的块必须能被认成某种零件**
   （`--new-track-min-score`，默认 0.60）。噪声不会被认成零件，
   这是比位置**更强**的一道。
3. **不一致**：检测帧传给追踪器的 `blobs` 是**外扩 ROI 内**的，
   而全图搜索那份是**全画面**的 —— 两套不一致。
   -> 现在明确分开：
     · **追踪用**的块：`blobs = [b for b in res.brass_blobs if _in_inset_roi(b)]`
     · **判丢用**的全图搜索：保持全画面（不能只看工位）
   ★ 两份**用途不同，不能混**。

> ★ 教训：**「在 ROI 内」要先问清 ROI 是怎么算出来的。**
> `work_roi` 是为「把木桌挡在外」而**外扩**的，
> 拿它当「新轨迹的合法区」用就太宽了 —— **一个区域的边界往往是按另一个用途定的**。

#### 另一个坑：为了支持「拿走又放回」把帧率弄刷到 9fps

为了让「拿走又放回原位」能恢复同一条轨迹，把 `gone` 轨迹保留 60 秒。
但 `_run_trackers` 判「值不值得跑 KCF」用的是 `lost_frames`，
而它**只在真检测到时清零** —— 于是被保留的轨迹**永远在跑 KCF**：

```
保留 gone 60 秒 -> 每帧均摊 82ms -> **9.1 fps**（用户感觉「等了一分钟」就是这个）
修：新增 miss_streak（连续多少帧**没拿到检测结果**）
     只在 miss_streak 小的时候跑 KCF；_adopt 与 _attach 都重置它
-> 9.1 -> **26.6 fps**
```

> ★ 一个字段被**两种语义抢用**的老问题（参 §2.24）：
> `lost_frames` 既想表示「多久没跟上」、又想表示「还值不值得跑」。
> **拆成两个：`lost_frames`（跟丢多久）与 `miss_streak`（多久没拿到检测）。**

### 2.29 ★★ 「全图搜 0 帧」橙色标记 + 幻影轨迹（第三次“一个计数器两种语义”）

**用户澄清**（我上一轮理解错了）：

> 不是去掉面板上的缺什么，而是不在画面显示某个物品缺失前的那个橙色标记
> 也就是全图搜多少帧。缺什么还是要在面板上显示的

→ 我把**面板**的「缺: xxx」误删了（已恢复）；要去掉的是**画面上**那个标记。

#### 「0 帧」的含义

`全图搜 0帧` = 这条轨迹**刚诞生、一次都没跟住过** —— 从噪声里生的。
修法：`draw()` 里对这类轨迹直接 `continue`，**完全不画**。

#### ★★ 第三次：`miss_streak` 不能在遮挡期间累计

实测：手盖住 60 帧 -> `miss_streak=60`；手一移开再过 30 帧就超过幻影阈值
—— **一个真实存在、一动没动的零件被删了**。

修：遮挡期间把 `miss_streak` **清零** —— **被遮挡不是不存在的证据**。

| 第几次 | 字段 | 被哪两种语义抢用 | 代价 |
|---|---|---|---|
| 1 | `lost_frames` | 「多久没跟上」vs「还值不值得跑 KCF」 | 拆成 `lost_frames` + `miss_streak`（§2.28） |
| 2 | `clear_frames` | 「多久没看见」vs「遮挡物移开多久」 | 改成按**真实秒数**（§2.25） |
| 3 | `miss_streak` | 「多久没检测到」vs「多久真的丢了」 | 遮挡期间清零 |

> ★ 一句好用的判据：**“看不见”有三种原因 —— 被挡、没认出、真不在。
> 三者对应三个不同的计数器，混用就会出这种错。**

#### 尝试过的两种错判据（都记在代码注释里）

| 错判据 | 为什么不行 |
|---|---|
| `not t.adopted_once`（从未被检测匹配过） | 轨迹**就是检测建出来的**，新建路径必然把它置为 True -> **条件永远不成立**，删除逻辑从来没跑到过 |
| `t.tracked_once`（KCF 报成功） | 实测：在**一帧纯灰背景**上（根本没有零件）
`cv2.TrackerKCF.update()` **依然返回 True** —— 它自己找个东西盯上。**不能用追踪器的返回值判幻影** |

#### 最终判据

```
not covered  and  miss_streak > phantom_miss_frames
默认 phantom_miss_frames = max(90, lost_grace_frames * 3)   # 生产配置下 = 90 帧 ≈ 3 秒
```

从宽限期**推导**而不写死：测试用的短宽限配置下会自动收紧，
不会因为一个写死的数字而让测试永远跑不到那个条件。

#### 另两道防幽灵的闸（§2.28 已记，补充实测）

* **位置：ROI 先内缩 6px** —— `work_roi` 是料盘**外扩 25mm** 的，挡不住边沿噪声。
* **身份：新轨迹的块必须能被认成某种零件**（得分 >= 0.60）。
  实测 `now_raw.png` 里料盘外那块 600px 的噪声
  **被认成 P2_column、得分 0.89** —— 只有位置闸能挡住它。
  工具：`tools/verify_allow_new.py`（逐块列出放行/拒绝及原因）

#### 另一个低级但会崩的错

`miss_txt` 在 `putText` **之后**才赋值 -> `UnboundLocalError`。
顺序错而已，但因为面板是每帧都跑的路径，**一崩就是全崩**。

### 2.37 ★★ 「D435 只能 26.4fps」是我的**测量开销**，不是相机上限；且 60fps 模式**规格表没列全**

**症状**：`d435_fps_bench.py` 报「640x480@30 / 848x480@30 / 1280x720@30 / 1920x1080@30
**全部都是 26.4 fps**」。

★ **这个形态本身就是证据**：三种带宽相差 4 倍的流给出**完全相同**的数 ——
不可能是相机限制，只可能是**测量方法**卡住了。

**根因**：那一版脚本在测量循环里**每帧都做 `np` 统计 + 存图**，
Python 侧的开销成了瓶颈，把相机真实帧率盖住了。

**修法**：纯读帧、不写盘、不做统计，并用**回调模式**（让 SDK 采集线程自己计数）
对照验证。两个测法给出同一个数才算数。

**实测（USB 3.2 / 固件 5.17.3.10 / 预热 2s + 测量 5~6s）**

| 模式 | 阻塞·全程 | 阻塞·稳定段 | **回调模式（绕开 Python 循环）** |
|---|---|---|---|
| **彩色 640x480@30** | 30.0 | 30.0 | **30.0** |
| **彩色 640x480@60** | 57.4 | **59.9** | **59.5** ← ★ 规格表里没有 |
| 彩色 424x240@60 | 59.5 | 59.5 | 59.5 |
| 彩色 1280x720@30 | 30.0 | 30.0 | 30.0 |
| 彩色 1920x1080@30 | 30.0 | 30.0 | 30.0 |

深度 / 红外（阻塞读帧，预热 2s + 测量 5s）：

| 模式 | 实测 |
|---|---|
| 深度 640x480@30 | 30.0 |
| **深度 640x480@60** | **59.9** ← ★ 规格表里没有 |
| 深度 848x480@60 | **59.9** ← ★ 规格表里没有 |
| 红外左目 640x480@60 | **59.9** |
| **★ 彩色 + 深度 同时 640x480@30** | 30.4 / 30.4 |
| **★ 彩色 + 深度 同时 640x480@60** | **64.5 / 64.5** |

★★ **三条结论**：

1. **`rs-enumerate-devices` 打印的 profile 列表不完整** —— 它只列了
   `640x480 → 30/15/6`，但**实际能开 60fps**（彩色、深度、红外都是）。
   ★ 教训：**「工具说支持哪些模式」不等于「实际能开哪些模式」** ——
   想要某个模式就直接 `cfg.enable_stream(..., 60)` 试一次，别只信列表。
2. 30fps 是**我们脚本自己设的**（`--fps 30`），不是相机限制。
3. **60fps 下每帧只给算法 16.7ms**（30fps 是 33.3ms），而工程实测
   **KCF 约 8ms/目标** —— 4 个目标就吃满 32ms。
   → **提高相机帧率不会让算法变快**，反而更容易把算法逼到掉帧
   （相机给 60 帧、算法只处理得动 30 帧，队列会堆积、延迟上升）。
   真正受益的是**手工快速摆放/遮挡**这种画面变化快的场景，
   以及「靠多帧投票去抖」的判据（样本数翻倍）。

工具：
- `用户存档/d435_fps_ceiling.py` —— 彩色帧率上限（阻塞 + 回调双测法）
- `用户存档/d435_depth_fps.py` —— 深度 / 红外 / 彩色+深度同时的帧率上限

★ **通用教训（比这条本身更重要）**：
**看到「多个差异很大的输入给出同一个数」，先怀疑测量，别先下结论。**

### 2.38 ★★ D435 的 640x480 是**裁切模式** —— 别拿 720p 的内参按像素数外推

**症状**：文档里一直写着「640x480 → 360mm 处 GSD **0.795** mm/px、覆盖 509mm」。
接进工程后用 `tools/probe_d435.py` 一量，**对不上**：

```
实测（USB 3.2 / 固件 5.17.3.10 / 相机对着桌面 / 自动曝光）
  模式          实测fps   fx      fy      GSD@360mm   覆盖@360mm      过曝
  640x480@30     30.0    603.8   602.4   0.596       382 x 286 mm   1.60%
  1280x720@30    30.0    905.7   903.7   0.397       509 x 286 mm   1.20%
```

**根因**：0.795 是**拿 720p 的出厂内参（fx=905.74）等比外推**得到的
（905.74 ÷ 2 = 452.87 → 360/452.87 = 0.795）。这个算法**默认两个模式 FOV 相同** ——
而 D435 的 640x480 **是裁切模式**：

| 模式 | 水平 FOV | 依据 |
|---|---|---|
| 1280x720 | **70.5°** | 2·atan(640 / 905.7) |
| 640x480 | **55.9°** | 2·atan(320 / 603.8) |

★ **同一台相机、不同分辨率的内参可以完全不同**（裁切/binning），
所以要 GSD 就必须**从 `get_intrinsics()` 读当前模式的值**，不能按像素数换算。

**判据 / 修法**：
* 每换一次分辨率 ⇒ **重读内参 + 重跑 c1/c3**（`TrayMap.mm_per_px` 全靠它）；
* `tools/probe_d435.py` 会把 fx/GSD/覆盖/过曝一起打出来，换模式后跑一遍就不会错；
* ★ 连带影响**选型**：640x480 的视野只有 **382mm 宽**（比 HBV 的 555mm 窄得多），
  而 1280x720 是 509mm —— 到工位要先量「料盘 + 装配位」占多宽，
  **超过 382mm 就只能用 1280x720**。

### 2.42 ★★ 尺寸闸门（`max_diam_mm`）：顺序、摆位、判据三个坑

> 背景：`docs/现状与交接.md 的 P1-1「开放位置」要求"尺寸闸门是放开 ROI 的前提"。
> 本轮（A 模块）把它做出来：`segment.max_diam_mm` + `segment.work_roi_mode`，
> 并让 `Segmenter.segment()` 收 `mm_per_px`。下面是实现过程中**实测踩到的三个坑**。

#### 坑 1（最重要）：闸门必须量「闭运算**之前**」的连通域

**症状**：全图模式（`work_roi_mode: full`）下，木桌被挡掉了，
但**贴着木桌的真零件也一起没了** —— 实测合成场景里 4 个零件只剩 2 个。

**根因**：`brass` 掩膜是 `inRange -> morph_open -> morph_close`，
而 `morph_close` 会把**相距 1~2px 的两块连成一块**。
木桌就贴在零件旁边（真机上木桌下沿 y=204 比料盘上沿 y=187 还低），
于是闸门量到的是「木桌 + 贴着它的零件」这**一整块**：

```
全图模式的连通域（量的是闭运算后的掩膜）：
   area    54252  Ø 65.7mm   bbox  707, 383 299x299   <- 轮盘，正常
   area    21061  Ø 40.9mm   bbox 1049, 408 263x257   <- 立柱，正常
   area   857960  Ø261.3mm   bbox    0, 711 1720x569  <- 木桌 + 底座 + 顶盖，整块超限
```

**修法**：`_mask(..., morph=False)` 单独出一份"纯色域骨架"给闸门量尺寸，
再用 `keep_mask` 去裁**闭运算后**的掩膜：

```python
raw_brass  = self._mask(hsv, self.brass, morph=False)   # 只用来量尺寸
brass_mask = self._mask(hsv, self.brass)                # 真正输出的
keep_mask  = self._size_gate(raw_brass, mm_per_px, max_diam)
brass_mask = cv2.bitwise_and(brass_mask, keep_mask)
```

★ **判据（可复用）**：**一个量几何的闸门，不能在"被形态学改造过"的掩膜上量。**
形态学的任务是"把该连的连起来"，而闸门的任务是"把太大的剔掉"——
两个任务方向相反，**共用一个掩膜必然互相破坏**。

#### 坑 2：摆位检查必须按「闭运算后 + 留间隔」

写 `tests/test_size_gate.py` 时，要往画面里画一块"假木桌"当被测对象。
第一版手工挑坐标（贴 ROI 下沿），结果**四个零件只剩 2 个**；
换到 y0=940 仍剩 3 个。原因是**料盘底沿的暗色部分也落在黄铜色域里**，
`morph_close` 往外扩 2~3px 就与假木桌连上了。

**修法**：不要手工试坐标，让测试**自己扫**一条干净位置：

- 用 **闭运算后**的掩膜（不是纯色域掩膜）判断"这一行是空的"；
- 还要求**上下各留 3px**（`morph_close` 核是 5，半径 2）；
- 再 `dilate(3x3)` 兜底复核一次。

★ **教训**：**"我看了这一行没有黄铜"不是判据** ——
要被测的那个掩膜（闭运算后的那个）说了算。

#### 坑 3：不要拿「质心处有没有像素」当"零件还在不在"的判据

`tools/verify_size_gate.py` 第一版这样判"这块被闸门剔掉了吗"：

```python
still = r_on.brass_mask[cy, cx] > 0        # cx,cy = blob.centroid
```

结果 `glove_miss.png` 上报 **"PART DROPPED"**，而同一行的
`dropped_px=0`（闸门**一个像素都没剔**）—— 两个结论自相矛盾。

**根因**：**轮盘的质心落在轮毂孔里**（它是环形件），那里本来就是背景。

**修法**：比**整块掩膜的重叠**（`bitwise_and` 后数像素），不看单点。

★ 这是本项目第 N 次「**判据选错 -> 假失败**」：
`docs/现状与交接.md` 的 P0-3（`nan` 来自空列表均值）、
实录 2.41（模块全过却报失败）都是同一类 ——
**「结论与旁边的数字互相矛盾」时，先怀疑判据，不要先怀疑代码。**

#### 真机对账（离线，不需相机）

`tools/verify_size_gate.py` 在仓库里的 5 张实录帧上跑，全图模式实测：

| 帧 | 超大块等效直径 | 判定 | 真零件最大 |
|---|---|---|---|
| `asm_raw.png` | **201.2mm** | 剔除 | 53.6mm |

### 2.43 ★★ D435 工位落地踩到的六个坑（2026-10，rev.3o）

> 背景：相机架到工位后，用 `ai_测试工具/` 的工具做对账与调参。
> 完整数字见 [`ai_测试工具/工位帧/工位实测记录.md`](../ai_测试工具/工位帧/工位实测记录.md)。

#### 2.43.1（最费时间）`Couldn't resolve requests` 不是"模式不存在"，是**设备被占用**

**症状**：`d435_intrinsics_check.py` 报设备正常（SN / 固件 / **USB=3.2** 都读得到），
但 `640x480@30` 与 `1280x720@30` 都开不了，报 `Couldn't resolve requests`；
而且相机**自报的彩色模式只有 1920x1080 一组**（5 种像素格式）。

**根因**：Windows 设置的**相机预览页**（提示写着「已启用**多应用相机模式**」）
通过 Frame Server **持有**了设备 —— 它按当前那一档开着，
所以别人**枚举得到、开不了别的档**。

**判据**：**关掉那个预览页之后立刻全恢复** ——
彩色模式从 1 档变成 **7 档 × 5 格式 × 6/15/30/60fps**，两个模式都开成功。

★ 排查顺序：① 关掉相机预览页 / RealSense Viewer / 没退干净的 python；
② 硬件复位（`probe_d435.py --reset`）；③ 拔插 USB。
**不要先去调分辨率** —— 那样查错方向。

#### 2.43.2 **AWB 的「读数」≠ 它真正在用的值**

**症状**：把 `realsense.controls` 按"读出来的值"填实（`white_balance: 4600`），
结果色域**又变了一次**：

| | 绿幕 H | 零件暖色 H 中位 | `brass` 掩膜 |
|---|---|---|---|
| 填之前（AE+AWB 自动） | **81** | **29** | **3994 px** ✅ |
| 填 4600 之后 | **87** | **6** | **58 px** ❌ |

**根因**：`4600` 是 **AWB 关掉那一刻的读数**，而 AWB 是**连续估计**的。
方向也自洽：WB 设低 ⇒ 红增益大 ⇒ 画面偏红 ⇒ 绿幕往青走（H 变大）、零件往红走（H 变小），
正好把 `brass` 的 `[10,45]` 从两头挤掉。

**修法**：**扫一遍**（`ai_测试工具/sweep_camera_controls.py --auto-wb` + 一组固定值），
最后靠**用户目视**定为 **6300**（配合 `v_min: 90`）。

★ 教训：**自动模式的瞬时读数不能当手动值用。**

#### 2.43.3 **别从截图量阈值**（我踩了）

**症状**：想从用户发的 5 张实况台截图里量出该调哪个阈值 —— 量出来完全不对。

**根因**：截图带**窗口边框**、还可能被**系统缩放**。
同一帧我从截图量到 `brass` **2369 px**，而用户 HUD 上写的是 **19488 px** —— **差 8 倍**。

**修法**：阈值只能在「**实时画面 + 当前真实分辨率**」下定。
为此把阈值也做成了实况台里**可键盘直调**的项（按 `f` 切「分割模式」）。

★ 截图只配用来**看现象**（闪不闪、切没切到），**不配用来量数**。

#### 2.43.4 边缘「**闪烁**」= 阈值卡在边界上

**症状**（用户原话）：「立柱和顶盖的**边缘会闪烁**」
「曝光 24 时闪，**曝光 28 基本不闪**」「对比度 50 时顶盖边缘闪、立柱检测不到边缘」。

**根因**：边缘像素的**亮度**（以及被高光洗过的饱和度）正好卡在阈值边界上，
噪声一飘就跨过阈值 ⇒ 同一个零件的边缘**一帧在内、一帧掉出去**。

**修法**：★ **不要用调曝光去迁就阈值**，而是改阈值本身：
- 用户在实况台上把 `v_min` 从 80 试到 **90**，配合 `exposure 126 / gain 28 / WB 6300` 后稳定；
- 边缘还碎就加大 `morph_close`（5 → 7 → 9，**必须奇数**）；
- ★ 注意 **`v_min` 与 `s_min` 方向相反**：`v_min` 提上去挡暗噪声、
  `s_min` 降下来保高光洗白的亮面 —— **别单独动其中一个**。
  出现"零件缺一块"（而不是"边缘闪"）时，第一件事是把 `v_min` 降回去试。

#### 2.43.5 **「颜色像真的」与「检测稳」会冲突 —— 必须选检测稳**

用户实测的四组对照：

| 目标 | 设置 | 结果 |
|---|---|---|
| 颜色最接近真实 | WB **6300** | ❌ 掩膜/轮廓有很大问题 |
| 检测好 | WB **5900** | ✅ 但不接近真实颜色 |
| 更像人眼 | 对比度 **50** | ❌ 顶盖边缘闪、立柱检测不到 |
| 分割最好 | 对比度 **40** | ✅ |

**判据**：这是**机器视觉系统**，判据只吃"掩膜切得全不全、稳不稳"；
`part_id` 的全部特征（`area_mm2` / `solidity` / `holes` / 色域）都建立在
**每一帧切得一样**之上。"像不像真实"是**主观**的，而"这帧切到、下帧切不到"是**客观失效**。

★ 本项目最终**仍选了 6300 + 对比度 50**（用户的取舍：要颜色真实），
靠 `v_min: 90` 把边缘稳住。**若现场又发现边缘闪，第一件事是把对比度降回 40。**

#### 2.43.6 用 `yaml.safe_load` + `safe_dump` 写配置会**清空所有注释**

**症状**：调试台的"按 `w` 写回配置"第一版用 `yaml.safe_load` + `safe_dump`，
写完之后 `camera.yaml` 里**所有 `★` 依据注释全没了**。

**根因**：`safe_load` 只解析数据，**注释在解析阶段就被丢弃**，`safe_dump` 自然写不出来。
这直接违反 `AGENTS.md §3`「改配置时保留 `★` 注释并更新依据」。

**修法**：改成**按行外科手术** —— 只把 `realsense.controls:`（或 `brass:`）那几行替换掉，
其余每一行原样保留；**连每行的行尾注释也原样留着**，只换数值。
实测：★ 数量 **81 → 81 不变**；写前自动备份 `.bak` 并逐项打印旧值→新值。

★ 附带发现：`live_site_debug.py` 的 `save_to_config` 还要处理
"原来的注释带对齐空格（`exposure: 156                  # 注释`）"这件事 ——
照抄会变成 `exposure: 61# 注释`（挤在一起），所以统一补成"键值 + 2 空格 + # 注释"。

#### 2.43.7 附带：一条**不用做**的事（省一整步）

★ **D435 的内参不用标定**：出厂 `fx=603.82` 与文档记的 `603.8` **逐位吻合**，
畸变模型 `inverse_brown_conrady` 但**系数全 0** ⇒ **校正已在相机里做完**，
再用 OpenCV 标一次等于**把校正做两遍**，精度只会更差。
★ 同理 **c2 双目标定整条作废**（深度由固件算，工程里 `right=None`）。
**真正要重跑的只有 c3（料盘单应）。**

### 2.44 ★★ 料盘挪动后「一个零件都识别不到」（2026-10，三个根因叠加）

> 症状：用户跑 `part_track_demo.py`，4 个零件**一个都没描出来**，
> HUD 显示「零件 1（可用 1 / 遮挡 0）| 手: 无 缺: wheel,column,base」。
> 而**前一天调相机参数时是能识别的**。

★ 用户的判断是对的、而且比我的初判准：「位置即身份，是**相对于料盘**的位置是身份。
料盘有纹理（立柱是斜的类椭圆，其他三个是圆形），料盘移动也要能检测到，
**你不能把料盘固定死**。」
—— 我一开始把 `work_roi` 说成"画面里的固定位置"，那是错的。

#### 2.44.1 根因一：ROI 根本没跟料盘走（**代码写错了**）

`tools/part_track_demo.py` 里：

```python
roi = q.work_roi_mask(frame.shape, 1.0,
                      pose=getattr(seg, "_last_pose", None), ...)
```

`seg` 是 `Segmenter` —— **它永远不会设置 `_last_pose`**（那是 `Qualifier` 的属性）。
于是这个 `pose` **恒为 None**，ROI 一直用 `calibration.yaml` 里的**静态标称坐标**。
所谓"位姿修正"**从来没生效过**。

**实测后果**（用户截图，料盘相对标定挪了 **(258, 58) px = (222, 50) mm**）：

| ROI | 范围 | 黄铜覆盖 | 零件落在里面 |
|---|---|---|---|
| 标称 ROI（现状） | x∈[238,607] | **0.5%** | **0/4** |
| 料盘轮廓 ROI（修法） | x∈[491,879] | **85.8%** | **4/4** |

**修法**：新增 `Qualifier.tracking_roi()`（`assemvision/core/checks.py`），
降级链 = **料盘自身轮廓 > 上次已知位姿 > 标称坐标**；
`part_track_demo.py` 的检测帧与"新轨迹只准建在工位内"那道闸都改用它，
位姿一变就清 `_roi_cache`。

★ 为什么"料盘轮廓"能打断死结：`segment_with_roi()` 的两遍分割**第一遍依赖标称 ROI**
（ROI 需要位姿、位姿需要零件、零件需要 ROI）—— 料盘挪远后第一遍切不到零件，
就永远停在第一遍。而料盘轮廓**不依赖零件、也不依赖 ROI**（全图直接跑）。

#### 2.44.2 根因二：**改白平衡让已采的色域模板全部作废**

立柱（块2）的 `c_hue_mean`：模板 **33.71~34.61**，实测 **19.04**。
轮盘的 `c_sat_hi_frac`：模板 **0.237~0.263**，实测 **0.944**。

**为什么**：`calibration.yaml` 的 `part_templates` 是在 **AWB 自动**时采的；
之后为了可复现把白平衡**锁成 6300K**（rev.3o），整幅画面的色相/饱和度全平移了。
色域特征**与尺度无关**，所以重跑 c3 也救不回来 —— **必须重跑 c6**。

#### 2.44.3 根因三：料盘距离变了 ⇒ GSD 变了 ⇒ 物理量按比例失真

两个**互相独立**的估计：

| 依据 | 实测 | 标称/真实 | 比值 |
|---|---|---|---|
| 料盘边长（`detect_tray`） | **232.3 px** | 185.6 px（160mm / 0.8623） | **1.252** |
| 轮盘外径（已知物理常数） | **88.8 mm** | 74.4 mm | **1.19** |

两个估计吻合（1.19~1.25）⇒ **料盘离相机比标定时近了约 20~25%**。
`area_mm2` 按 k² 放大（1.57 倍）、`length_mm` 按 k 放大 ⇒ 全部越出模板区间。

★ 判据：**只要有一个"已知物理尺寸"的物体（料盘 160mm 或轮盘 Ø74.4），
就能当场反推 GSD 偏了多少** —— 比重新标定快得多。

#### 2.44.4 根因四（方法学）：**用真图算出「改善了」≠ 推导对了**

我从截图看到"轮廓 ROI 4/4 圈住零件"，就宣布推导（标称中心被抵消）成立。
**写测试时发现两处判据错误**：

1. **ROI 位移 ≈ 1.10 × 料盘位移**，不是 1:1 ——
   因为 `tx` 用 `mm_per_px` 换算、而 `mm_to_px` 又用**单应自身的尺度**投回去，
   两个尺度不自洽（1.098 / 1.1317 vs 0.8623）。
2. **ROI 质心本就不等于料盘中心**（实测差 **37 px**）——
   ROI = 料盘四边形（外扩 25mm）**+ 装配位圆**，质心被那个圆拉偏。

所以正确的断言是「**ROI 必须含住检测到的料盘中心**」+「面积量级不崩」，
而不是"质心相等"。改成这个判据后，三个位移与"标称单应过期"场景全部通过。

★★ **教训：能写成断言的性质就去写断言。** 肉眼看图会替你把错误判据合理化 ——
本轮我因此返工三次（`test_tracking_roi.py` 的 v1/v2/v3）。

★ 附带一个测试环境坑：**画布必须装得下挪动后的料盘**，否则 ROI 被画面边界裁掉，
"含住料盘中心"当然不成立 —— 那是**测试场景建错**，不是代码坏（第一版用 640×480、
把料盘挪到 (740,340)，假失败）。
