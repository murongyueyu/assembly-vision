### 2.1 背景是绿幕，不是黑底

| | 实测值 |
|---|---|
| 绿幕 | H 中值 **83**（p2–p98 = [79, 95]）、S 中值 **255**、V 中值 224~242 |
| 黄铜零件 | S 分布 **[52, 109]**，中值 80~92 |

- 黄铜的 `s_max` 取 **180**。**不能取 90/110** —— 那样会削掉零件自己的高光（实测零件 S 上限 109）。
- `s_max` 之所以能挡绿幕：绿幕 S≈255，与零件 S≤109 之间有 75+ 的余量。
- `segment.py::_mask()` **曾经不读 `s_max`**（配置写了不生效），已修好。改 `_mask()` 时注意保持
  默认值 `h_max=179 / s_max=255 / v_max=255`，否则会破坏老配置。

### 2.2 黄铜假阳性靠阈值切不干净

原木桌面与手臂肤色的 S 中值 **67~87**，与零件 S 区间完全重叠。
演示阶段画面里有笔记本和木桌时，实测假黄铜块达 17883 / 8443 / 7937 px。

**根治办法是给黄铜检测加"工位全局 ROI"**（托盘 + 装配位的包围盒），而不是继续调阈值。
正式工位简化成"绿卡纸 + 黑料盘 + 工件"后此问题基本消失，但**换环境要重新确认**。

### 2.3 蓝手套与笔记本键盘背光/屏幕的色相完全重叠

| | H | S | V | 面积 |
|---|---|---|---|---|
| 真手套 | 92~99 | 134~246 | 91~255 | ~110000 px |
| 键盘背光 | 91~104 | 121~174 | 81~146 | ≤ 9052 px |
| 笔记本屏幕 | 96~100 | — | 81~148 | 47652 px |

**色相分不开，只能靠 V 下限 + 面积闸门。** 实测扫描后取 `glove.v_min: 130`：

```
v_min=110 -> 真手套 83316 px | 空场景最大蓝块 7882 px  ✗ 会过面积闸门
v_min=130 -> 真手套 79638 px | 空场景最大蓝块 1230 px  ✓
```

> 正式工位不放笔记本后此风险消失，但 `v_min=130` 保留（真手套只损失 4%），
> 用来兜住"操作人员的手/袖子/其它蓝色物体"。

### 2.4 深度只用 SGBM，StereoBM 不可用

料盘表面几乎无纹理（料盘区 Laplacian 方差 **156**，只有整幅 2490 的 6%），
局部块匹配器没有可比对的特征：

| 匹配器 | 整幅有效像素 | 料盘区有效 | 过 `min_valid_ratio` 闸门? | 料盘区视差散布 |
|---|---|---|---|---|
| StereoBM（原实现） | **7.8%** | 9.3% | **✗ 否**（闸门 0.2） | **75 px（纯噪声）** |
| **SGBM** nd=256 bs=5 | **22.7%** | **45.8%** | ✓ 是 | **6.6 px** |

已改为 SGBM，并把 `min_valid_ratio` 降到 **0.12**。**不要在 480×360 以上算深度**：
实测 SGBM 1280×960 要 476 ms，按树莓派 4B 慢 6 倍估约 2.9 秒，不可用。

### 2.5 相机的分辨率与拼接方式（实测，反直觉）

| 请求 | 实际 | 帧率 | 单眼 | 真双目? |
|---|---|---|---|---|
| 2560×960 | 2560×960 | **4.5 fps** | 1280×960 | ✅ |
| 2560×720 | 2560×720 | 4.5 fps | 1280×720 | ✅ |
| 1920×720 | →1280×720 | 48.7 fps | 640×720 | ✅ |
| 1280×960 | 1280×960 | 31.3 fps | 640×960 | ⚠️ 视场窄，左眼装不下料盘 |
| 960×960 | 960×960 | 32.0 fps | — | ❌ 单眼画面 |

**★★ 最终选用 `1280×480`（单眼 640×480）—— 与 `predict.py` 一致。**
判据是**左眼能不能看全料盘**（算法全程只用左眼）：

| 请求 | 单眼 | 左眼里的料盘 | 结论 |
|---|---|---|---|
| **1280×480** | 640×480 | 177×178 px（占宽28%） | ✅ **采用** |
| 1280×960 | 640×960 | 301×314 px（贴右边缘被切） | ❌ |
| 2560×960 | 1280×960 | — | ❌ **数字放大**，最糊 |

**三个反直觉点**：
1. **`2560×960` 不是真高分辨率，是数字放大**。判据：把高清缩回低清尺寸与原生低清比，
   差仅 **1.7**（几乎同一幅画）；而 `1280×960` 同法对比是 **26.6**（真不同）。
   再佐证：锐度 **1280×480=242 > 1280×960=125 > 2560×960=89**（越高越糊）。
   **分辨率高 ≠ 细节多**，判断真伪必须做"降采样回比对"。
2. **必须用左眼判断视场**，别用"完整拼接图看起来能放下" —— 算法只用 `f.left`。
3. **`scale.realtime` 会影响标定窗口里画面的大小**：取 0.5 时单眼 640×960 被缩成 320×480，
   标定窗口里料盘只有一半大，**看起来像"视野被裁了"，其实内容是全的**。标定取 **1.0**。

**帧率随 OpenCV 版本差异极大**：同一台相机，OpenCV **4.12** 下 2560×960 只有 **4.5 fps**，
OpenCV **5.0**（yolo 环境）能稳在 **31.9 fps**。**本项目统一用 yolo 环境的 OpenCV 5.0。**

### 2.6 料盘槽位实测（★ 2026-10 修正，原配置四个槽的零件归属全错）

**实测布局（用户确认）**：**左上=轮盘 / 右上=立柱 / 左下=顶盖 / 右下=底座**
原 `workpiece.yaml` 写的是 左上=立柱 / 右上=轮盘 / 左下=底座 / 右下=顶盖 —— **全错**，
导致覆盖率算出来 0.11~0.69，明明有件却判"缺件"。

**实测方法**（可复用）：用 c3 单应把空料盘图**正交化成 160×160mm 正视图**（4 px/mm），
再做"凹陷检测"（大核背景减除 + 逐象限 Otsu）拟合每个槽的 `minAreaRect`。
实测结果与零件名义尺寸交叉吻合（轮盘 Ø74.4↔槽Ø75、底座 Ø59.3↔槽Ø65、立柱长85↔槽91）：

| 槽位 | 中心 (tray mm) | 形状 | 实测尺寸 | 原配置（错） |
|---|---|---|---|---|
| slot_wheel 轮盘 | (42,43) | 圆 | **Ø75** | Ø74.4 @ (120,40) |
| slot_column 立柱 | (120,39) | 对角胶囊 | **91 × 28 @ -44°** | 85.2×15.6 @ (40,40) |
| slot_cap 顶盖 | (39,127) | 圆 | **Ø25** | Ø19.1 @ (120,120) |
| slot_base 底座 | (121,122) | 圆 | **Ø65** | Ø59.3 @ (40,120) |

> ★ 槽位**中心**原本基本正确（±3mm），主要错在**零件归属**和**尺寸**。

**★ `tools/make_synthetic.py` 的 `SLOTS` 字典必须与 `workpiece.yaml` 同步**：
测试的做法是"用 `SLOTS` 渲染合成图 → 用 `workpiece.yaml` 的槽位算覆盖率"，
两边不一致就误判（实测踩过：改 yaml 没改 SLOTS，`test_segment`/`test_polar` 立刻挂）。

### 2.7 镜面高光会去饱和，`s_min` 不能太高

实测 `slot_base` ROI 内，`V>200` 的高光像素有 **1874** 个，其 **S 中值只有 20**（范围 [4,59]）。
`s_min=60` 会把它们全部拒掉 → 底座覆盖率被压到 0.37（实际有件）。

**`s_min: 50`**（原 60）：底座覆盖率 0.37 → **0.49**，而**空料盘四槽仍是 0.00**（不会误判有件）。

> ★ **但不要靠放宽 `h_max` 来补救**：实测 `h_max=65` 时**空料盘开始出现 0.04~0.05 的假覆盖率**，
> `h_max=70` 直接崩到 0.41~0.86（料盘表面被当成黄铜）。`h_max` 保持 **45**。

**★ 调试覆盖率要用 `tools/tune_slots.py`**：把"槽位几何 / 分割阈值 / 零件摆放"三者
放在同一个实时画面上，改一格立刻看到覆盖率变化。**不要拿零件没摆好的截图调参**
（实测踩过：在一张立柱没摆好的图上扫 `s_min`/`h_max`，越调越偏）。

### 2.8 料盘位姿自动补偿：不再依赖"料盘固定不动"

**为什么必须有**：整套判定原本建立在"料盘位置和朝向固定"上（c3 标一次单应，之后所有
槽位 ROI 都按那次算）。**实测踩过**：料盘在 c3 之后被挪了约 18mm ——
关键是**相机没动**：

```
绿幕质心   c3 (362.4,277.1) -> 现在 (366.2,272.8)   只差 3.8px   ✓ 相机没动
料盘暗区中心 c3 (417.5,258.5) -> 现在 (399.5,266.0)  差 18px      ★ 料盘动了
```

后果：四个槽的 ROI 全偏 18~20mm，覆盖率从 0.6 掉到 0.2，**明明有件全判"缺件"**。

**做法**（`assemvision/core/tray_pose.py`）：**零件本身就是最好的基准点**。

```
① 第一遍：不依赖槽位坐标，按形状/面积/色域特征识别每个黄铜块"是什么零件"
② 把「实测质心」与「标称质心」配对，最小二乘解料盘刚体变换 (θ, tx, ty)
③ 第二遍：用变换修正所有槽位 ROI，再算覆盖率与判定
```

**为什么用刚体变换而不是重算单应**：

- 只解 **3 个自由度**，4 个零件给 8 个观测 -> 超定，稳
- **不会把误识别放大成畸变**（单应 8 自由度、4 点恰好定解，一个点错就整体歪）
- 料盘本来就是刚体

**实测验证**（真实画面，故意把标称槽位偏移，看能否找回）：

```
标称偏移 (   0,   0) -> OK 4/4   估计 Δ( -1,  +0)  残差 0.2mm
标称偏移 (+25,   0) -> OK 4/4   估计 Δ(-26,  +0)  残差 0.2mm
标称偏移 (  0, -30) -> OK 4/4   估计 Δ( -0, +30)  残差 0.2mm
标称偏移 (+30, +25) -> OK 4/4   估计 Δ(-31, -25)  残差 0.2mm
标称偏移 (-20, -15) -> OK 4/4   估计 Δ(+19, +15)  残差 0.2mm
```

**偏移多少就报出反向多少，残差恒定 0.2mm。**

**★ 两个必须注意的点**：

1. **旋转矩阵的符号**：图像坐标系 **y 轴向下**，常规数学的 `[[c,-s],[s,c]]`
   在这个坐标系里对应的视觉旋转是 **-θ**。所以 `TrayPose.R` 用 `[[c,s],[-s,c]]`。
   符号写反的症状：模拟料盘转 +7.5°，估计器却报 -7.5°，**残差高达 14.7mm**。
2. **零件被全部拿走时没有基准**（装配完成后）：此时沿用最后一次成功的位姿
   （`pipeline._last_pose` 缓存）。只认到 1 个零件时定不了旋转，只能定平移 ——
   所以缓存只在 `n_used >= 2` 时更新。

**能力边界**：至少认出 2 个零件才能定旋转；1 个只能定平移；0 个则 `ok=False`
（**绝不瞎猜**，退回标称坐标）。认错零件时残差会很大（实测 124mm）自动 `ok=False`。

### 2.9 零件识别：旋转不变的特征向量（不靠固定槽位坐标）

**为什么需要**：只靠"槽位 ROI 覆盖率"判定有个硬前提 —— **料盘位置和朝向固定**。
料盘转一下、相机被碰一下、零件在槽里放歪，ROI 就全错位。

**做法**（`assemvision/core/part_id.py`）：用**旋转不变**的特征向量判定"这是什么零件"，
位置另用 ROI 判。三个判据叠加：`覆盖率` + `特征识别` + `几何形状检查`。

**特征选择原则 —— 只能用转多少度都不变的量**：

| 用 | 特征 | 说明 |
|---|---|---|
| ✅ | `holes` 内孔数 | 拓扑量。轮盘 8+ 孔、底座 1 孔、顶盖 0 孔 —— **最可靠** |
| ✅ | `elongation` 伸长率 | 只用长宽比不用角度。立柱 ~3.2，圆件 ~1.0 |
| ✅ | `area_mm2` 物理面积 | = 像素面积 × mm_per_px²。**区分同为圆形的底座与顶盖的唯一手段** |
| ✅ | `solidity` / `circularity` | 形状比例 |
| ✅ | **色域** `c_hue_mean` / `c_sat_mean` / `c_val_mean` / `c_hue_std` | 颜色天然旋转不变，补材质/氧化差异 |
| ❌ | `rect_angle` | **绝对角度**，料盘一转就变 |
| ❌ | 质心坐标 | 位置另用 ROI 判 |

### 2.10 ★★ 特征稳定性随零件形状而变（立柱是弯曲+锥形+台阶，不是圆柱）

**这是本轮最重要的教训 —— 我曾把稳定性排序搞反了。**

**零件真实形状**（用户手机照片确认）：机加工件，**左端螺纹+法兰 → 锥形过渡 →
长圆柱轴（表面抛光纵向亮纹）→ 右端明显弯折（约 15~20°）→ 细颈+螺纹头+小法兰**。
即 **B（台阶）+ C（锥形）+ E（非回转）** 三种叠加。

**后果**：分割**只切得到圆柱顶面那条高光带**，两侧暗部切不到。所以：

```
长边变化  -1.7%   ✓ 稳（由两端最远点决定，端点永远在）
宽边变化 -30.3%   ✗ 漂（取决于哪条亮纹被切中被切中）
```

**合成实验量化**（合成立柱，只改"被照亮的宽度比例"从 100% 到 40%）：

| 特征 | 相对变化 | 评价 |
|---|---|---|
| `feret` / `rect_long` | **3.9~4.0%** | ✓✓ 最稳（只依赖两端点） |
| `elongation` | 18.0% | ✗ 含宽度因子 |
| `solidity` | **21.0%** | ✗ ★ 见下方警告 |
| `rect_short` | 22.0% | ✗ 含宽度因子 |
| `circularity` | 39.3% | ✗ |
| `area` | **51.5%** | ✗✗ 最不稳 |

**★★ `solidity` 是"圆件上稳、细长弯曲件上不稳"**：

```
圆件（轮盘/底座/顶盖）实测波动  2.2%   ✓
立柱实测波动                   21%    ✗
```

**我一开始拿"跨零件平均波动"（2.2%）当结论，把 `solidity` 当成全局最可靠特征并给了
3.0 权重 —— 那个 2.2% 是拿圆件平均出来的，对立柱恰恰是错的。**
症状：立柱在两次实测间得分 1.00 → 0.48，直接"认不出"。

**解法：逐零件权重**（`PartTemplate.weights`，从 `calibration.yaml` 的
`part_templates.<零件>.weights` 读）：

```
P2_column:  area_mm2 0.1   solidity 0.2   circularity 0.2
            length_mm 4.0  elongation 2.0  short_side_mm 0.5
```

轮盘/底座/顶盖仍用全局默认（`solidity` 是它们的主判据，权重 2.0）。

**新增两个"只依赖端点"的特征**（`features_from_blob`）：

- `length_mm` —— 最长边物理长度。**对细长/弯曲/锥形件唯一可信的特征**，权重 2.5
- `short_side_mm` —— 短边物理长度。圆件上稳（波动 0.4~4%），
  区分顶盖(Ø25) 与底座(Ø65) 一类"同形状不同大小"

**区间半宽也要按"该零件该特征的实测波动"定，不能统一 ±3%**：

```
solidity ±10% | end_width_ratio ±15% | circularity ±25%
elongation ±35% | area_mm2 ±30%（★ 再大轮盘与底座区间会完全重合）
length_mm ±8%  | short_side_mm ±8%
```

> ★ **`solidity`/`circularity` 是比例量，区间上限必须截断到 1.0**
> （算出来 1.056 是物理上不可能的）。
> ★ **立柱的 `elongation` 上限单独放宽到 5.0**：实测 4.74 系高光带导致偏高，
> 而轮盘上限只有 1.36 —— 放宽后仍**互不重叠**（这是它有效的关键）。

**★★ 逐零件权重曾经静默失效**：`checks.py::_classifier()` 建
`PartTemplate` 时**漏传了 `weights`**，所以配置里写死了也不生效。
改这块时务必确认权重真的传进去了（`clf.templates[i].weights` 非空）。

**验证结果**（两组独立实测特征）：

```
旧（统一 ±3% 区间 + 全局权重）: c6第1次 4/4 但本次实测 2/4
                                （立柱 0.48 认不出、底座被认成顶盖 0.90）
新（实测波动定宽 + 逐零件权重）: 两组都是 4/4，得分 1.00
```

**★★ `area` 的归一化踩过三次坑**（`features_from_blob` 里有完整记录）：

1. 用 **bbox 面积** → 圆的"面积/bbox面积"恒为 π/4 ≈ 0.785，**与大小无关**
   → 底座（Ø59.3）和顶盖（Ø19.1）算出来一样大，互相误判。
2. 用 **料盘面积** → 对坐标映射的**尺度**极敏感（同一张合成图在 4.0 与 2.5 px/mm 下
   算出 0.328 与 0.127）→ 底座被判成顶盖。
3. 用 **该槽面积** → 尺度无关、朝向无关，但仍区分不了同为圆形的底座与顶盖
   （各自都填满自己的槽）。
4. ✅ **最终用 `area_mm2`（物理面积）**：实测跨尺度稳定（2.5/4.0 px/mm 下
   4380 / 4377 mm²，差 0.06%）。

**★ 色调 H 是环形量，必须用圆统计**：H∈[0,179] 里 0 和 179 其实相邻，
直接取平均会得到完全错误的值（5° 和 175° 的平均是 90°）。
`color_features()` 把 H 映射到单位圆求平均向量。

**★★ 覆盖率阈值必须按槽缩放**（`check.coverage_scale_by_max`）：

覆盖率 = 零件面积 / 槽面积，**每种零件天生不同**：

```
轮盘 4378mm² / 槽 Ø75     -> 最大约 0.99
底座 3244mm² / 槽 Ø65     -> 最大约 0.98
顶盖  462mm² / 槽 Ø25     -> 最大约 0.94
立柱 1311mm² / 槽 91x28   -> 最大只有 0.51   ★ 细杆 vs 宽胶囊槽
```

用统一的 `coverage_present=0.45` 卡，**立柱完整在位也只有 0.40 → 必然误判存疑**（实测踩过）。
缩放后立柱阈值 ≈ 0.38，完整在位稳过。

**★ 测试朝向鲁棒性时只转轮盘，不要转立柱**：
真实工位里**槽是固定的**，把零件转出槽口范围会被槽壁截断，覆盖率必然下降 ——
那是几何事实，不是"识别不了朝向"。轮盘的**辐条图案**是唯一朝向敏感的特征。
而且要用 `render_scene(wheel_rotate_deg=...)` 做**几何**旋转，
不要用 `warpAffine` 转掩膜（离散网格上的孔洞合并/锯齿伪影会让测试假失败）。

### 2.11 c6 零件特征标定：必须核对"零件有没有放对槽"

**实测真实画面的特征值**（c6 第 1 次，零件均在正确槽位）：

| 零件 | area_mm2 | elongation | circularity | solidity | holes |
|---|---|---|---|---|---|
| P3_wheel 轮盘 | **3265** | 1.01 | 0.47 | 0.79 | 0 |
| P2_column 立柱 | **1074** | **3.36** | 0.46 | 0.90 | 0 |
| P4_cap 顶盖 | **555** | 1.08 | 0.83 | 0.96 | 2 |
| P1_base 底座 | **3155** | 1.11 | 0.79 | 0.96 | 2 |

- **轮盘 3265mm² 反推 Ø64.5mm**，**立柱 1074mm² 反推约 85×12.6mm** ——
  与实物尺寸一致（轮盘 Ø74.4 / 立柱 85×15 在**透视投影 + 分割侵蚀**下略小）。
- ★ **`holes` 在真实画面上的表现与合成图完全不同**：实测是 **轮盘 0 / 立柱 0 / 顶盖 2 / 底座 2**，
  而合成图是 9/0/0/1。说明 `count_holes` 的判据（自适应阈值 + 面积下限）
  在真实光照下数不出轮盘的辐条间孔。**所以不要依赖 holes 区分轮盘**，
  实际区分靠 `elongation`（立柱 3.36 vs 其余 ~1.0）和 `area_mm2`。

**★★ 必须核对零件放对了没有 —— 这是踩过的坑**：
连续跑三次 c6，第 1 次零件摆对（几何自洽），第 2/3 次零件位置全换了
（`P2_column` 变成 `elongation=1.01` 的圆件、`P1_base` 变成 `elongation=6.3` 的细长件），
而脚本**每次都照旧写入 `calibration.yaml`**，把好数据覆盖成垃圾模板。

**★★ 「交叉验证 100%」是假信号，不能作为可信依据**：
那段逻辑是「用刚采的样本造模板 → 用这个模板认同一批样本」，**循环验证必然 ~100%**，
**哪怕零件全放错、哪怕某个槽空着，也照样报 100%**。
它的唯一作用是"检查特征区间有没有互相重叠到认不出来"。

**真正判断零件放对没有，靠「物理尺寸对账」**（c6 的 `采集质量自检` 一节）：
由实测面积反推直径/长宽，与零件的名义尺寸比对。

```
第1次(零件都对)     -> ✓ 通过
   轮盘 实测 圆 Ø64.5mm   应放 槽 Ø75      ✓
   立柱 实测 细长 60x18mm 应放 85x15 细杆   ✓
   顶盖 实测 圆 Ø26.6mm   应放 槽 Ø25      ✓
   底座 实测 圆 Ø63.4mm   应放 槽 Ø65      ✓
第2次(挪位)         -> ★ 拒绝写入（4 项全不符：轮盘位置实测 Ø27、底座位置实测 Ø26…）
第3次(空槽+挪位)    -> ★ 拒绝写入（轮盘槽没采到样本 + 3 项不符）
```

自检不通过时脚本**打印报警并 `return 2`，不写文件**（避免覆盖好数据）。

> ★ **名义尺寸取自 `workpiece.yaml` 的 `slots`，不要用 `radii_mm`**：
> 实测发现 `radii_mm.cap=9.55`（Ø19.1）与 `slots.slot_cap.diameter=25` 自相矛盾，
> 而真实画面量出顶盖 **Ø26.6mm** —— 和槽的 Ø25 吻合，说明 **`radii_mm` 那个值是错的**。
> 容差放宽到直径 [0.55, 1.20] 倍（实测因**透视投影 + 分割侵蚀**会偏小 10~20%）。

重跑前先确认：
- 四类零件按 `slot_wheel=轮盘 / slot_column=立柱 / slot_cap=顶盖 / slot_base=底座` 摆好
- **料盘正放、不要整盘旋转**（槽位坐标是按正放标定的）

> ★ 合成图上的 `test_segment` 现在只判覆盖率、不判零件识别 ——
> 因为合成几何与真实几何差得多（合成轮盘 4377mm² vs 真实 3265mm²），
> 真模板认合成图会"认不出"（分 ~0.3）。**这是 `min_score` 门槛在正确工作**
> （认不准就不猜），不是 bug。

### 2.12 工位全局 ROI：黄铜只在「料盘 + 装配位」范围内检测

**这是 2.2 早就写明该做、直到实测踩到才做的一件事。**

**为什么必须有**（实测真实画面）：木桌的 HSV 与黄铜重叠，**画面顶部的木桌整块被判成黄铜**：

```
实测某帧的连通域:  (认不出) 面积 13269mm²   ← 真零件最大才 3281mm²，4 倍
                  P4_cap   面积  1503mm²   ← 顶盖应是 555，被木桌污染
```

后果：零件识别错（底座被认成轮盘）、面积测量全废、位姿估计算出**荒谬的 48° 旋转**
（而这又触发了 `max_theta_deg` 闸门，见 2.8）。

**为什么不用调阈值**：单独收紧 `h_max`/`s_max` 会削掉零件自己的高光
（实测零件 S 上限 109、H 上限 45，与桌面区间本就重叠）—— 按下葫芦起瓢。
**ROI 是「位置即身份」**，与颜色、光照都无关。

**为什么不用「按固定比例裁掉上下 15%」**：可行，但**余量太薄**：

```
实测料盘底沿到画面 y=376px，"中间 70%" 只到 408px —— 只差 32px
料盘稍微往下挪一点就被切掉
```

而 ROI 外扩 25mm（≈29px）且**跟着位姿补偿一起动**，余量随料盘走。

**实现**（`segment.work_roi_margin_mm`，默认 25mm）：

```
core/segment.py    segment(..., work_roi=mask)  ->  brass_mask &= work_roi
core/checks.py     Qualifier.work_roi_mask()    ->  料盘外扩 + 装配位外扩的并集
                   Qualifier.segment_with_roi() ->  两遍：几何ROI粗分 -> 定位姿 -> 细分
pipeline.py        T3 算 ROI 缓存到 _work_roi，T2 下一帧用它分割
```

**★ 为什么是「两遍」而不是一遍**：ROI 需要位姿（料盘可能被挪动），
而位姿又需要分割结果 —— **先有鸡还是先有蛋**。
解法：第一遍用**几何 ROI**（不依赖位姿）粗分，够用来估位姿；
第二遍用估出的位姿修正 ROI 再细分。
第二遍还有个保护：**只有前景面积没明显变小才采用**（防止 ROI 反而切掉零件）。

**★ pipeline 里 ROI 是"隔一帧"生效的**（T3 算、T2 用）：料盘逐帧变化很慢，
差一帧完全够；而且**宁可"不限制"也不要"限制错"** —— 限制错会把真零件挡在外面。

**写这条的测试时踩的两个坑**（`tests/test_work_roi.py`，都是测试的问题不是 ROI 的）：

1. **合成图画布默认只留 12mm 边距** —— "画布内、ROI 外"的区域几乎不存在，
   于是"放在 ROI 外"的位置其实落在料盘 ROI 里，测不出效果。
   -> 必须用**大边距画布**（`margin_mm=80`）。
2. **只判断"在 ROI 外"还不够** —— 还要确认该处在**不带 ROI 时真的会被切成黄铜**。
   否则放了个空位置（画面外/黑边），前后都是 0，看着像"ROI 没生效"。
   -> 候选点必须**用不带 ROI 的结果筛一遍**。

### 2.13 ★★ 装配体上"数辐条"：为什么要用**金属掩膜**（曾数不出 8 峰）

**症状**：c5 第二步在装配位上数辐条，`spoke_peak_count = 0`（应为 8）。
`--diag` 扫各半径带的峰数：`8~16→0  12~20→0  16~24→0  20~28→5  24~32→3  28~36→1`
**没有任何一条带能数出 8 峰。**

**★ 根因：球头被拍到了，但颜色被绿垫污染，过不了 `h_max=45`。**

沿半径同时量"黄铜占比"和"非绿占比"（非绿 = 不是绿垫 = 有金属）：

```
半径mm   黄铜%   非绿%        ← 关键：黄铜切不到，但"有东西"
  28~30    19.7    72.5
  30~32     4.8    41.4
  32~34     0.5    22.2
  34~36     0.0    16.3       ★ 球头在这里，只是没被切成黄铜
  36~38     0.0    13.0
```

外圈带 28~40mm 里"非绿"占 **27.3%**，其 **H 中值 59、S 中值 85、V 中值 222**。
**那个 `H=59` 是关键** —— 不是"中性白"，是**被绿垫染成淡绿色的金属**
（H 59 紧贴绿垫的 60~100）。球头只有 **Ø5mm**，在 0.86mm/px 下
**只有 6 个像素宽**，边缘抗锯齿后整颗球都被绿垫混色 → 被 `h_max=45` 整条挡掉。
外圈环厚约 2mm = **2.3 像素**，同理。

**★ 解法：`metal_mask`（"亮 + 不是绿垫"，不看色相上限）。**
实测同一帧在 30~35mm 带对比：

```
brass 掩膜:  峰 4   抖动 52.5°
metal 掩膜:  峰 8   抖动  5.9°   [5.5, 57.5, 98.5, 134.8, 176.5, 219.5, 262.0, 310.0]
```

间隔 52/41/36/42/43/43/48/56° → 平均 ~45°，是**真辐条**不是凑数。

**★★ 判据的准确形式（我在这里连续踩了三个坑）**：

```
metal = (v >= v_min) & (s <= s_max) & (~green)
green = (h 在 [g_lo,g_hi]) & (s > g_smin)
```

| 写法 | 漏掉了什么 | 后果 |
|---|---|---|
| 只判 `~green` | **木桌**（H=19,S=122,V=210）色相不在绿区间 → 成了"非绿" | 木桌区 metal 占比 **99.9%**，扫优全废 |
| 加 `V>=v_min` 但仍只判 `~green` | **黑底**（H≈0,S≈0）也是"非绿" | 合成图整幅变金属 → 端到端从 OK 掉成「辐条 0/8」 |
| ✅ 再加 `s<=s_max` | —— | 三种背景都正确 |

`s_max` 实测扫描（木桌区 metal% vs 30~35mm 峰数）：
`200→99.9%/8峰  140→99.3%/8峰  120→44.6%/8峰  100→15.2%/8峰` → 取 **100**。

> ★ **木桌最终是靠 `work_roi` 几何挡掉的（位置即身份）**，
> `s_max` 只是第二道防线 —— 不要把安全性全押在颜色上。

**★ 回落条件是"有没有内容"，不是"是不是 None"**：
绿垫以外的背景（深色底、黑垫）上 metal 判据正确地什么都匹配不到
→ mask 是**全 0 的数组而不是 None**。写成 `is not None` 就会拿空掩膜去数辐条。
判据用 `np.count_nonzero(mask) > 200`。

**★ 装配体上"数臂"也不行**：臂与臂之间的空隙里看到的是下方的底座圆盘
（同样是黄铜），在装配体上用臂的环带数只会得到"整圈都是金属"→ 一个峰都数不出来。
**必须数"球头端伸出外圈的凸起"**。

**★★ 一个容易搞错的点**：`assembly_flags()`（判 `wheel_present` 谓词）
用的是 **`self.r_spoke` = `assembly.radii_mm.spoke_band`（12~24mm）**，门槛 `>= 4`；
而 `check_assembly()`（终检）用的是
**`self.r_spoke_out` = `assembly.radii_mm.spoke_band_outer`（30~35mm）**。
**两个不同的半径带、两个不同的用途**，改的时候别混。

> ★ `spoke_band_outer` 原写 **33~37.5mm**，是**从没验证过的假设值**，
> 落在球头最外沿（~37mm）之外 → 数不出峰。实测应为 **30~35mm**。
> ★ `sweep_band` 原来**只看"峰数 == 8"**，会把**凑出来的 8 个峰**当好的
> （brass 28mm 带是 8 峰但抖动 33°）。现在加了**角度均匀度**判据：
> 间隔相对 360/8 的抖动 > 12° 直接排除。

### 2.14 ★★ 过曝会让**整条判据链静默失效**（不是"少切一点"）

**实测踩过，这是 c5 反复失败的真凶**。曝光 -5.0 在某次工位光照下严重过曝：

```
曝光    过曝%    V均值   brass总px   轮盘那块px
 -3    92.58     254        0            0
 -5     7.96     244     1308          626   ← 轮盘真值约 3200px，只剩 1/5
 -6     0.00     216     9619         3094   ← 正确
 -7     0.00     157     9897         3104
```

**后果链**：

```

     -> 装配体上数辐条恒为 0 峰、brass 面积塌到 1/5 -> c5 全线失败
```

**而界面上只是"看着亮一点"**，完全看不出判据已经废了。

**★ 判据：近全白像素（`min(BGR) >= 250`）必须 ≈ 0%。**
`segment.detail` 里会记 `blown_ratio` / `v_mean`，报警阈值取 **0.5%**。
`tools/preview.py` 与 c4/c5 的预览窗口在超阈值时**整屏描红边 + 大字报警**。

环境变亮就要往更负调。**换工位、换时段、开/关灯都必须重扫。**
实测某次光照下 -5.0 就过曝，而更早那次 -5.0 是正常的 —— **别以为"上次好用"就永远好用**。

**★ 画面里的高亮区域会把相机测光带偏**：实测画面左侧有一面白墙，
整幅均值被拉到 BGR 217/244/97。**白墙不参与检测，但会毁掉曝光** ——
能挡就挡，或者把测光区域改成 ROI 内（本项目尚未做，暂时靠手动曝光兜）。

### 2.15 ★★ `run_calib.ps1` 是 UTF-16LE，**不要用普通文本编辑器改写**

**实测踩过，后果严重**：用 UTF-8 编辑器改这个文件后，它从 **UTF-16LE + BOM**
变成 **UTF-8 无 BOM**，而 **PowerShell 5.1 读无 BOM 的 UTF-8 会按 ANSI 解码**
→ 中文注释全乱码 → 引号配对错乱 → **脚本直接不可运行**（报"字符串缺少终止符"），
而且**中文内容会实质丢失**：

```
原始: FF FE 23 00 20 00 ...   6740 字节   UTF-16LE + BOM
改后: 23 20 72 75 6E 5F ...   4121 字节   UTF-8 无 BOM   ★ 中文丢了
```

**正确改法**（保持 UTF-16LE）：

```powershell
$t = [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::Unicode)
$t = $t.Replace($old, $new)
[System.IO.File]::WriteAllText($path, $t, [System.Text.Encoding]::Unicode)
```

**★ 如果已经改坏了，`git checkout` 可能修不回来** —— 工作区字节被转码工具动过，
而 git 凭 stat/hash 判断"内容相同"就跳过还原。可靠做法是从 blob 取原始字节，
并**确认前两字节是 `FF FE`**：

```powershell
git cat-file blob "HEAD:assembly_vision/run_calib.ps1" > $tmp
# ★ 必须再校验：$tmp 的字节可能被重定向转码破坏
[System.IO.File]::WriteAllBytes($target, [System.IO.File]::ReadAllBytes($tmp))
```

**★ 改完 `.ps1` 一定要跑一次解析检查**（PowerShell 只在真正执行时才报错，
那时你会以为是"别的地方的问题"）：

```powershell
$t=$null; $e=$null
[System.Management.Automation.Language.Parser]::ParseFile($path, [ref]$t, [ref]$e)
$e.Count   # 应为 0
```

> `.md` / `.py` / `.yaml` 都是 **UTF-8**，用普通编辑器改没问题。
> **只有 `.ps1` 是 UTF-16LE** —— 改之前先确认编码，别一刀切。

### 2.18 ★★ 数辐条：**不能把半径带切成几份投票**（真机"装好了却判缺辐条"）

**症状**（真机 `app.py --windowed`）：轮盘明明完整装好、8 根辐条清晰可见、
界面显示"装配流程全部完成 4/4"，但实际报的是：

```
辐条峰数 0/8        齐套性: NG, 缺失 辐条 5/8
（连续几十帧都是 0~7，**8/8 一次都没出现过**）
```

**★ 根因：`count_spokes` 把半径带切成 `n_radii_bands=3` 个子带各自数峰，
再「取众数、并列时取较小值」** —— 而这个偏置在这里会**稳定地少数**。

实测（真机装配体 `asm_raw.png`，30~35mm 切成 3 带，每带仅 **1.67mm ≈ 1.9px**）：

```
带(mm)        med    p95-med  阈值    峰数
30.0~31.7    0.000   1.000   0.600    8   <- ★ 球头只落在最内侧这个带
31.7~33.3    0.000   1.000   0.600    6
33.3~35.0    0.000   1.000   0.600    5
```

计数 `[8, 6, 5]` —— **三个全不同、没有众数** -> 并列取较小值 -> **5**
-> `5 < required(8)` -> **装好的轮盘被判"缺辐条 5/8"**。

而**同一帧整条 30~35mm 一次数**（c5 的做法）是 **8 峰、抖动 5.9°**。
**两边做法不一致，所以 c5 数出 8、`check_assembly` 数出 5。**

**★ 物理原因**：球头只有 **Ø5mm**，在 0.8623mm/px 下**只有约 6px 宽**，
落进哪个子带**是碰运气** —— 最内侧那个 1.9px 的子带恰好切到了它。

**★ 解法：按「角度均匀度」挑最好的带，而不是让几个带投票取小。**
真辐条的**角度是均布的**，所以"抖动最小"远比"票数最多"可靠：

```
select=vote(旧)     -> count=5  抖动=inf   峰=[98, 135, 177, 262, 309]
select=uniform(新)  -> count=8  抖动=6.2°  峰=[6.2, 57.2, 99, 135, 177, 218, 262, 309]
```

6.2° 与 c5 当初**独立**扫出的基线（抖动 5.9°、峰
`[5.5, 57.5, 98.5, 134.8, 176.5, 219.5, 262, 310]`）几乎逐度吻合 —— **互为独立验证**。

**★ 这个"均匀度"判据不是新发明**：c5 的 `sweep_band` 早就用它
（`真辐条抖动 5.9° vs 凑出来的 8 峰抖动 33°`）。
这次只是把**同一条判据搬到 `check_assembly` 的路径上**，
让两处**用同一个标准** —— 之前它们不一致正是 bug 的温床。

**保留 `select: vote`** 以便对比与回退（`workpiece.yaml` 的 `check.spokes.select`）。
**默认是 `uniform`，不要改回去。**

**★ 兜底不能少**：如果**所有**候选带的抖动都超过 `max_jitter_deg(15°)`，
说明这一圈本来就不规整（真缺辐条 / 被遮挡）——
此时**退回"峰最多"那个**，让缺陷被如实报出来，
而**不是**因为我们挑剔就报成 0（那会变成另一种假 NG）。

**★ 验证**（真机帧上跑完整 `check_assembly`）：

```
修复前: verdict=NG   missing=[辐条 5/8]
修复后: verdict=OK   spoke=8/8  抖动=6.2°  missing=[]
```

而合成图上"少画 0/1/2/4 根 -> 数出 8/7/6/4"**全部仍然准确**，
真缺陷的检出没有因为这次改动而变差。

> ★ 一般教训：**同一个量在两个地方用了两套算法，迟早会打架。**
> c5（标定）与 `check_assembly`（运行）都在数同一批辐条，
> 却一个"整条带一次数"、一个"切 3 带投票"，所以标定时是 8、运行时是 5。
> **标定与运行必须共用同一条判据** —— 这是比这次具体的阈值更重要的结论。

> ★ 另一个教训：**"并列时取较小值（宁少不多）"这类偏置要写清适用条件。**
> 它在"没有真值可依"时是对的（宁可漏报不要误报），
> 但这里我们**有**更强的几何信息（辐条是均布的），
> 这时"取小"就变成了**系统性地少数**。

### 2.19 ★ 零件识别用的是什么方法、准确率多少（可复现的量化）

**方法：旋转不变的特征向量 + 区间匹配 + 加权打分。没有神经网络。**

```
features_from_blob(blob)  ->  特征字典
PartTemplate.score(feats) ->  (总分, 各特征得分)      # 区间匹配 _band_score
PartClassifier.classify() ->  (part, score, detail)   # 取最高分；< min_score 则返回 None("认不出")
```

**判据三层叠加**（缺一不可，`check_slots` 里）：
1. **覆盖率**（位置即身份）——该槽里有没有东西
2. **特征识别**（本节）——那东西是什么零件
3. **几何形状检查**——形状自洽（如立柱的细长比）

**特征清单**（`calibration.yaml` 的 `part_templates.*.ranges`，由 `c6` 标定产出）：
`circularity / solidity / elongation / holes / end_width_ratio / aspect /
area_mm2 / area_frac / c_hue_mean / c_hue_std / c_sat_mean / c_val_mean /
c_sat_hi_frac / length_mm / short_side_mm`

**全局特征权重**（`calibration.yaml` 的 `part_id.feature_weights`）：
`holes 2.0 / elongation 2.0 / area_mm2 1.8 / solidity 1.5 / c_hue_mean 1.4 /
circularity 1.2 / c_sat_mean 1.0 / end_width_ratio 1.0 / ...`
**逐零件权重**覆盖全局（目前只有立柱有，见 §2.10）。

#### 实测：合成序列端到端（精确真值）

工具：`python tools/measure_part_id_e2e.py`（真值来自槽位几何，与分类器无关）

```
TP 该有且认对 = 9      TN 该缺且没认到 = 168
FN 漏检       = 3      FP 误检         = 0
★ 准确率 (TP+TN)/全部 = 177/180 = 98.3%
★ 召回率（有件时认对） = 75.0%      ← ★ 这个才是有意义的那个数
★ 精确率（认对/所有认出）= 100.0%   ← 零误检
```

> ★ **98.3% 这个数被"168 个空槽正确地空着"抬高了** ——
> 报告准确率时**必须同时给召回率与精确率**，否则会误导。
> **零误检（FP=0）比高准确率更重要**：宁可说"认不出"，也不要认错。

3 个漏检的明细：`f009~f011`，轮盘槽里那个零件被认成 `P1_base`。
**根因是合成图自己的几何问题**（见下），不是分类器：

```
make_synthetic.SLOTS 的槽心  vs  workpiece.yaml 的标称槽心：
   P3_wheel   Δ=(-4.60, +3.50)   距离  5.78 mm
   P2_column  Δ=(-3.20,+10.30)   距离 10.79 mm
   P4_cap     Δ=(-6.00, +3.20)   距离  6.80 mm
   P1_base    Δ=(-9.50, +0.60)   距离  9.52 mm
```

**判据**：拿**渲染真值**直接解位姿也报 `θ=-2.02° / 残差 3.1mm`；
把合成槽心当标称再解一次就是 `θ=+0.00° / 残差 0.0mm`。
-> **那 ~2° 与 ~3mm 完全来自"合成几何 vs 标称几何"的不一致**，
与估计器、与分割都无关。

> ★ **合成序列不能当"真机准确率"用** —— 它测的是**判据正确性**。
> 真机准确率只能在真机上现跑（`--live`，用「零件落在哪个槽」当真值）。

#### 实测：料盘旋转 / 平移检测能力

工具：`python tools/measure_rotation.py`（直接喂已知真值的质心，无渲染/分割噪声）

```
① 旋转 ±20°（步长 1~5°）：角度误差 最大 0.0000° / 平均 0.0000°
② 平移 ±30mm            ：误差     最大 0.0000 mm
③ 边界：
   3 件（少轮盘）      ok=True    θ=+8.00° 用3件 残差 0.0mm
   2 件（少轮盘+顶盖）  ok=True    θ=+8.00° 用2件 残差 0.0mm
   1 件（只剩底座）    ok=True    θ=+0.00° —— **只定平移，旋转定不了**（有偏）
   0 件（全拿走）      ok=False   绝不瞎猜
   真转 30/40/48°      ok=False   被 max_theta_deg=25° 闸门挡住（**有意的保护**）
   底座认成顶盖的位置  ok=False   残差 31.8mm -> 自动判不可信
```

> ★ **为什么隔离测试的误差恰好是 0.0000°**（不是"碰巧"）：
> 这是**往返测试** —— 用 `TrayPose.apply` 造数据、再用 `estimate_pose` 解回来。
> 它证明的是**解算器实现正确**（能精确解回它自己应用的变换），
> **不构成"真机旋转精度"的结论**。真机旋转精度要在真机上测。

#### ★★ 两个"我测错过"的教训（别重犯）

1. **`render_scene(wheel_rotate_deg=...)` 转的是"辐条图案"，不是料盘。**
   零件质心不动 -> 位姿**本来就该报 0°**。拿它测整盘旋转，
   会得到"θ 恒为 -2.0°、与真值完全无关"这种自相矛盾的表格。
   同理 `rotate_deg` 转的是**立柱**（源码自己注明是"研究几何用"）。
2. **改用"整幅图几何旋转"之后又被合成几何的 5.8~10.8mm 偏差污染。**
   于是凭空多出 ~2°/3mm 的固定偏差。

   -> **测一个纯几何算法，就直接喂它输入**（质心），
      不要在它外面套一层"渲染 + 分割"再声称测的是它。

#### 怎么在真机上量准确率

```bash
python tools/measure_part_id_e2e.py --live --frames 60
```

把 4 个零件摆进各自槽里，它会用「零件落在哪个槽」当真值逐帧统计

**不看位置就能认出**（P1-1 的前提）它也一并验证：不落在任何槽里的零件会被单独计数。
