**另修 2（★ 教训：`app.py --windowed` 长期没被任何测试覆盖）**：

一跑就连崩**两次**，两次都是「跨模块接口不一致」：

```
(1) TypeError: OpenCVRenderer.__init__() got an unexpected keyword argument 'actions'
    app.py 是**无条件**把 actions={...} 传给 make_renderer() 的，
    而 OpenCVRenderer 没有这个参数。--windowed 的默认渲染器就是 opencv
    -> **这条路径根本跑不通**。QtRenderer 有 actions，所以只有 opencv 版是坏的。

(2) AttributeError: 'OpenCVRenderer' object has no attribute 'frames_drawn'
    OpenCVRenderer 没调 super().__init__()，而 Renderer.__init__ 里设了 frames_drawn，
    Renderer.run() 靠它做 --max-frames 计数。
    QtRenderer 是 QMainWindow 子类、链路里自然调到了基类 -> 又只有 opencv 版是坏的。
```

**修法**：给 `OpenCVRenderer` 加 `actions` 参数并**真的接到按键上**
（`i` 手动抽检 / `r` 复位 / `q`·ESC 退出，与 QtRenderer 的按钮同义），并补 `super().__init__()`。

##### ★★ 必须先解决的一处**文档自相矛盾**

`part_tracker.py` 模块 docstring 第 29 行仍写着：

> `backend` 可选 mosse/kcf/csrt：**Pi 上建议 `mosse`（2ms）**或 `kcf`（12ms）。

而 **§2.21 的实测结论是「后端只有 `kcf` 可靠」**：
MOSSE 的 `update` **恒返回 False（实测 40/40 全丢）**。

→ **上面那句「Pi 上建议 mosse」是过期的错误建议**，动手时必须一并改掉，
否则接手的人会照着它去选一个已知不能用的后端。

##### 为什么「KCF 不好用」是真的 —— 已累计的三条实测证据

1. **每目标固定成本高**：实测 **5.5ms/目标**（另一处记 8ms），4 个目标 **≈35ms/帧**；
   且**与整帧尺寸无关**，所以降分辨率省不下来。
2. **裁剪加速已试过并放弃**：裁剪后**只快 14%，但静止漂移从 2.76px 崩到 131px**
   （裁剪窗滑动逼着反复 `init`，而 init 既不快又破坏追踪器状态）。
3. ★★ **它的返回值不可信**：在**一帧纯灰背景上（根本没有零件）
   `cv2.TrackerKCF.update()` 依然返回 `True`**
   —— 所以**绝不能用 KCF 的返回值判断"零件还在不在"**
   （这一点曾导致幻影轨迹判据失效，见实录 §2.27~2.29）。

★ 但也要记下 KCF 的一个优点：它是目前**唯一**在真机上稳定跑通的（中位 **28.9fps**、
相机上限 31），换掉它之前必须证明替代品在**遮挡与身份冻结**这些场景上不退化。

##### ★ 「识别只需要前面识别就好」这一步的**代价**（必须一起考虑）

本项目已经被"检测不够频繁"咬过两次，都是**幽灵轨迹**类问题：

- §2.27：缺件不报 —— 判据用的是"轨迹在不在槽里"，而不是**全图检测的权威结果**
  → 修法：缺件必须用 **`seen_ids`（来自全图检测）** 判。
- §2.28 / §2.29：料盘外的幽灵轨迹 + 「全图搜 0 帧」标记
  → 修法：新轨迹的块**必须先能被认成零件**（0.60），且 `miss_streak`
  **不能在遮挡期间累计**。

→ 所以「识别只做一次」**不是免费的**：检测频率一降，幽灵轨迹的温床就变大。
**可保留省算力收益、又不塌掉判据的折中方案**：

1. **低频复检（关键事件触发）**：抽到工件、放到装配位、遮挡解除，
   或面积/位置残差越过门限时，**强制跑一次全图检测**。
2. **检测间隔不可任意拉长**：`detect_every_n` 应有上限，超过就应改为**按时间**
   而不是按帧 —— 换 D435 后相机可到 60fps，同样 `every_n=5` 在 60fps 下是
   **12 次/秒**、在 30fps 下是 6 次/秒，**语义完全不同**。
   ★ 这是换机后新出现的坑，动手时必须一起处理。
3. **身份只在"够可信"时重判**：沿用现有三档（>=80% 重判 / 55~80% 沿用 /
   <=55% **冻结**），<=55% 那档本来就是"不重判"，与用户诉求方向一致。

##### ★★ 对比协议（用户明确要求「要有数据」）

**先声明接口，再换实现** —— 否则测出来的差异分不清是算法还是调用方式造成的。

### 3.2 零件检测的已知弱点
1. **`holes` 区间宽度≈0** —— 真机上同一零件数出 0/1/2/3 个孔，
   而 c6 把区间收成 `轮盘/立柱 [-0.0002, 0.0002]`、`顶盖/底座 [1.985, 2.015]`。
   **`holes=1` 时四个零件全部 < min_score（认不出）**，受控实验已证实。
   ★ 刻意改法（受控实验有效、真机 12/12 不损失）：**放宽到容忍 ±1**。
   ✅ **已改**（提交 `735925d`）：`part_id.holes_tol: 1`、底座 `2`，新增
   `tests/test_part_id_tol.py` 与诊断工具 `tools/measure_holes_gap.py`。
   ★ 那个提交自己列的收尾项里，**`docs/踩坑实录.md` §2.30 至今没写**
   （而 8 处代码注释都在引用它；§2.30 这个号已被 D435 占用）—— 接手时补一篇新号即可。
2. **`visible_ratio` 类的"参考值自我拉低"** —— 见实录 2.20 的 bug 1，
   PartTracker 里已修；但**同类写法在别处出现都要警惕**。
3. **木桌仍在画面上方**（y 0~204）—— 现在靠工位 ROI + 尺寸闸门挡。
   用户提过"裁掉上方就行"，但实测**木桌最低到 y=204，比料盘上沿 y=187 还低**，
   单靠裁剪挡不干净（裁到 205 会切掉料盘上沿 18px）。
   -> 若要做，**保守裁 `y >= 100` + 保留工位 ROI**（待用户决定）。

### 3.3 修掉的真 bug（累计）
都是**真机或空跑暴露出来的**，不是重构：

1. **`hub_coverage` 恒为 `nan`** —— c5 里 `rings.append(a.hub_coverage)` 复制粘贴漏改，
   三个覆盖率**全部错位**。（教训：看到 nan 先数列表里有几个元素）
2. **装配位 `pose` 不一致** —— `check_assembly` 用标称坐标、`work_roi_mask` 跟位姿，
   同一装配位两处算出不同的圈（料盘挪 8.8mm 时差 10px）。
3. **`app.py --windowed` 一启动连崩两次** —— `actions` 参数 + `frames_drawn` 未初始化。
   ★ 根因是**那条路径从没被任何测试覆盖**。
4. **"装好了却判缺辐条"** —— `count_spokes` 把半径带切 3 份投票取小，
   球头只落在最内侧 1.9px 的子带 → 数成 5 根。改为按**角度均匀度**挑带（§2.18）。
5. **`visible_ratio` 恒为 1.0**（追踪器）—— 语句顺序写反，参考值被遮挡后的小面积
   拉低 → 状态永远 `detected` → 每帧拿残缺件重判身份 → **认错**
   （遮挡 50% 时 `P3_wheel` 认成 `P2_column`）。见实录 **2.20**。
6. **`score_ema` 没初始化** —— 新轨迹直接赋值不走 `apply_id()`，
   `score_ema` 恒为 0 → "换标签要高出一截"的闸门**永远为真**。见实录 2.20。
7. **完全遮挡时可见度不降** —— 手套把零件盖死时仍显示「可见 100%」。见实录 2.20。
